iChat / Architecture plate / 2026.07

认证不是一道门，
而是一条可恢复的路径。

Auth 模块同时管理身份、短期凭证、邮箱所有权与邮件投递。真正的边界不在某个路由，而在事务提交：提交前可以整体撤销，提交后投递失败也不能改写 API 的成功。

核心判断

PostgreSQL 保存事实，Redis 只保存短期防滥用状态，Celery 只负责搬运任务。

因此 Redis 或 broker 暂时不可用时，系统仍能依据每条路径的风险选择 fail-open、fail-closed 或由 outbox sweep 恢复。

Signal rail

七条请求路径

切换一条路径，观察请求脉冲经过哪些层。节点按真实调用顺序排列；事务边界、失败策略与最终响应会随路径一起变化。

Responsibility

三层，不越界

当前实现把“HTTP 怎么说”“业务要做什么”“底层原子动作怎么完成”分开。邮箱流程比普通登录多一层用例编排，是因为它横跨限流、事务与异步投递。

Truth & failure

事实与故障

理解 Auth 的捷径，是先分清哪些数据代表业务事实，哪些只用于加速或抑制滥用；再看每个外部依赖失效时，请求应继续还是拒绝。

不可破坏的不变量

  1. A
    原始 token 不入库

    auth token 与 refresh token 都只保存哈希；原始邮箱 token 只出现于一次性的邮件链接。

  2. B
    同用途只有一个 active token

    重发先撤销旧 token；PostgreSQL partial unique index 为并发竞态兜底。

  3. C
    验证必须匹配当前邮箱

    token 未过期、未使用、未撤销，且 sent_to_email 等于用户当前邮箱，才设置 email_verified。

  4. D
    邮件先落 outbox，再异步发送

    API 成功以数据库 commit 为界；Celery 任务只携带 outbox_id，不携带业务内容。

依赖失效时怎么走

REGISTER / REDIS

IP 限流 fail-open；邮箱 cooldown 改查 PostgreSQL，优先保证注册可用。

RESEND / REDIS

fail-closed，返回 429。重发不是关键转化路径，宁可暂拒也不放大邮件滥用。

VERIFY / REDIS

fail-open。验证 token 具有高熵，不应因限流存储故障阻断用户。

DB / BEFORE COMMIT

rollback 整个事务，并尽力删除已经取得的 cooldown key，然后原样抛出错误。

BROKER / AFTER COMMIT

记录 warning，但 API 保持成功；pending outbox 由 celery-beat 的 sweep 后续重投。

HTTP contract

接口速查

所有成功响应都包在 { "data": ... } 中。Bearer access token 保护 /me 与重发接口；邮箱未验证不会限制聊天功能。
