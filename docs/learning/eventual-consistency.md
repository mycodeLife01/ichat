# 最终一致性：以番剧追更为例

> 学习笔记，**不是规则**。项目规则见 `docs/architecture/`，番剧追更的设计事实以
> [spec](../specs/2026-11-18-anime-tracking.md) 为准。本文只引用 spec 章节号，不复制字段与参数；
> 两者冲突时以 spec 为准。

## 0. 一句话结论

番剧追更的链路跨越 PostgreSQL、Redis/Celery、OpenList/PikPak、Telegram 四个系统，它们之间没有
共享事务。设计不追求「每一步都同时成功或同时失败」（强一致），而是保证：

> **无论在哪一步崩溃、丢消息、变慢或重复执行，系统最终都会收敛到正确状态，且不重复做不可撤销的事。**

这就是工程上说的最终一致性。下面先讲问题从哪来（§1），再给出一个心智模型（§2），然后用七个
具体场景拆解常用模式（§3），最后讲什么时候不必用这些模式（§4）、这份设计是怎么改进的（§5）。

阅读建议：第一次读按顺序；回顾时直接看 §7 速查清单和 §8 自测题。

## 1. 问题从哪来

### 1.1 四个系统，没有共享事务

```
蜜柑 RSS ──> PG ──> Redis/Celery ──> OpenList ──> PikPak
                                       │
                      PG <─────────────┘
                      │
                      └──> Telegram
```

PG 的事务只管得到 PG 自己。「写一行到 PG」和「发一条 Celery 消息」「调一次 OpenList」
「发一条 Telegram」都无法放进同一个事务里一起提交或一起回滚。

### 1.2 远程调用有三种结果

本地函数调用要么返回、要么抛异常。远程调用多了第三种：

| 结果 | 含义 |
|---|---|
| 成功 | 拿到了响应，对方确实做了 |
| 失败 | 拿到了错误响应，对方确实没做（或明确拒绝） |
| **不知道** | 超时、连接断开、自己在等响应时崩溃——对方**可能做了，也可能没做** |

大部分一致性问题都来自第三种。

### 1.3 只有三类故障

不管系统多复杂，要防的故障只有三类：

1. **崩溃**：进程在任意两行代码之间消失（`kill -9`、OOM、部署重启）。
2. **慢**：进程没死，只是卡住，慢到别人以为它死了。
3. **重复**：同一条消息被投递两次，同一个任务被两个 worker 执行，同一个请求被重试。

## 2. 心智模型

### 2.1 PG 是事实源，消息只是加速器

项目的所有后台任务都用同一个骨架（见 `docs/architecture/background-tasks.md` §1）：

```
事务性状态行（PG，事实源） + 唤醒信号（消息，可丢失） + 幂等 claim
```

- **状态行**：任务存在与否、进行到哪一步，只看 PG。
- **唤醒信号**：Celery 消息只是告诉 worker「有活了，快来」。丢了只会变慢，不会出错。
- **幂等 claim**：worker 用原子的条件 UPDATE 抢到一行才干活，重复执行无害。

推论：**任何正确性都不能依赖消息送达**。每一种消息背后都要有一个周期扫描兜底。

### 2.2 一个通用检查方法

> 在第 N 步和第 N+1 步之间 `kill -9`，或者让第 N 步卡住 10 分钟，系统会怎样？

把链路上每一对相邻步骤都问一遍，答不上来的地方就是缺口。spec §13 P0 验收第 3 条
「在 `submitting` 状态 `kill -9` anime-worker」就是把这个问题变成了可执行的测试。

## 3. 七个模式

每个模式按同一结构写：**场景 → 天真写法 → 出了什么错 → 设计怎么挡住 → 原则**。

### 3.1 先提交，再投递，加兜底扫描

**场景**：`poll_feed` 拉到新的一集，要写入下载任务，并通知 worker 去提交（spec §7.1）。

**天真写法 A：先发消息，再提交事务**

```
10:00:00.000  投递 submit_download(dl_42)
10:00:00.005  worker 收到，查 dl_42 → 查不到（事务未提交）→ 丢弃
10:00:00.010  事务提交
结果：一行 pending 永远没人处理
```

**天真写法 B：先提交事务，再发消息，但信任消息**

```
10:00:00.000  事务提交，dl_42 = pending
10:00:00.001  投递时 Redis 正在重启 → 消息丢失
结果：同上
```

**设计**：用写法 B，并**承认消息会丢**。beat 周期任务 `maintain_downloads` 扫描到期的
`pending` 行，把漏掉的补投出去（spec §7.4）。

| 情况 | 结果 |
|---|---|
| 消息正常送达 | 几秒内开始提交 |
| 消息丢失 | 最多晚一个扫描周期（5 分钟） |
| 两者同时发生（消息迟到 + 扫描补投） | 幂等 claim 保证只有一个 worker 真正执行 |

**原则**：会丢的东西不承担正确性。正确性只依赖 PG，消息只决定快慢。

### 3.2 唯一约束，代替「先查后插」

**场景**：同一个种子同时出现在两个订阅源里，两个 `poll_feed` 并发运行。

**天真写法：插入前先查**

```
        worker 1                         worker 2
t1   SELECT … WHERE infohash=abc → 无
t2                                   SELECT … WHERE infohash=abc → 无
t3   INSERT abc
t4                                   INSERT abc
结果：两个下载任务，下两份，收两条通知
```

「查」和「插」之间有窗口，别人能插进来。这叫 **check-then-act 竞态**。

**设计**：`anime_downloads.infohash` 唯一约束 + `INSERT … ON CONFLICT DO NOTHING`
（spec §6.3、§7.1）。PG 当裁判：后到的插入等前一个事务结束，发现冲突就什么都不做。
只有真正插入成功的一方投递唤醒消息。

**同一份 spec 里的反例**：`episode_dedupe`（spec §7.2）要防的是「同一集、不同字幕组」。两个
资源 infohash 不同，唯一约束管不到；「这一集是否已有任务」只能先查再插，于是竞态原样存在。
spec 的处理是**明确接受**：P0 只有一个订阅源，几乎不会发生（为什么可以接受，见 §4）。

**原则**：并发下「我检查过了」没有意义，除非检查和写入是原子的。能交给数据库约束的不变量，
不要写成应用层的 `if`。

### 3.3 事务性 outbox：事实和义务一起落库

**场景**：检查发现云端下载完成，要把状态改成 `completed`，并安排一条完成通知（spec §7.4）。

**天真写法：分两次提交**

| 顺序 | 两次提交之间崩溃 | 结果 |
|---|---|---|
| 先 `completed`，再 `notify_status=pending` | 状态已完成，通知状态仍是 `none` | 兜底只扫 `pending`，**通知永远不会发** |
| 先 `notify_status=pending`，再 `completed` | 下载仍是 `running`，通知已待发 | **通知说下好了，其实没下好** |

**设计**：一条 UPDATE、一次 COMMIT，同时写入 `completed` 和 `notify_status=pending`
（spec §6.4 末段）。提交之后才投递 `notify_download`；投递丢了由兜底扫描补投。

```sql
UPDATE anime_downloads
SET status = 'completed', completed_at = now(), notify_status = 'pending', …
WHERE id = :id AND status = 'running';
COMMIT;
-- 之后才投递 notify_download
```

「下载完成」是事实，「欠一条通知」是这个事实带来的义务，两者必须同生同死。这就是
**transactional outbox** 模式。

注意边界：真正调用 Telegram **不在事务里，也不可能在**。事务只保证「欠一条通知」被可靠记下；
发送由之后的步骤完成。

项目里有两种 outbox 形态：

| 形态 | 例子 | 适用 |
|---|---|---|
| 独立表 | `email_outbox`（`app/services/email/outbox.py`） | 产生副作用的业务各不相同，统一投递 |
| 状态行上的一列 | `anime_downloads.notify_status` | 副作用与某一行一一对应 |

**原则**：凡是「改状态 + 产生外部副作用」，在改状态的同一事务里记下「副作用待完成」，
再由可重试的步骤去完成它。

### 3.4 中间状态 + 对账：处理「不知道」

这是整份设计里最难、也最值得理解的一点。

**场景**：worker 调用 OpenList 为 dl_42 发起离线下载（spec §6.5）。

```
10:00:00  worker 调用 submit_offline(magnet)
10:00:01  OpenList 收到请求，PikPak 创建离线任务 ✅
10:00:01  响应还在网络上……
10:00:01  worker 被 kill -9
```

PikPak 已经在下载，PG 里却没有任何痕迹。请求 30 秒超时、但对方其实已经处理成功，也是同样的
局面——这就是 §1.2 的「不知道」。

**天真写法：靠状态顺序解决，两头都有洞**

| 做法 | 崩溃点 | 后果 |
|---|---|---|
| 提交成功后再写 `running` | 提交成功、写库之前 | 行仍是 `pending`，恢复后重提 → 云端两个任务 |
| 先写 `running` 再提交 | 写库之后、提交之前 | 库里说在下，云端什么都没有 → 干等到停滞上限 |

**设计**：引入一个专门表达「不知道」的状态 `submitting`。

```
1. 置 submitting + 写租约，单独提交事务        ← 先把「我要动手了」落库
2. 调用 submit_offline
3. 成功 → 置 running，写云端任务引用

恢复时发现 submitting 且租约已过期：
   不直接重提 → 先问外部世界 find_existing(infohash, target_dir)
     找到 → 补写 running（上次其实成功了）
     没找到 → 才重新提交
```

「本地状态不确定时，去查外部系统的事实来补全」叫 **对账（reconciliation）**。支付系统里完全同构：
订单有「支付中」状态，超时后不直接重扣，而是先调渠道的「查单」接口。

**这个方案的软肋**：对账依赖外部系统「查得到」。如果 OpenList 在任务完成或重启后清空了任务列表，
`find_existing` 会说「没找到」，于是重复提交。所以 spec 预设了三层降级（spec §6.5 第 5 步）：

1. 对账（依赖 S0-6 验证可查询性）；
2. PikPak 对同一 infohash 去重（依赖 S0-3 验证）；
3. 都不成立：接受崩溃窗口内可能多一份文件，写进 ADR。

最理想的是远程接口自带**幂等键**（如 Stripe 的 `Idempotency-Key`：同一个键重复请求只执行一次）。
PikPak 没有，只能用 infohash 近似。

**原则**：跨系统的副作用无法回滚，也无法与本地事务原子提交。能做的是：先落库意图，结果不明时
对账，并尽量让远程操作本身幂等。

### 3.5 租约与 fencing：租约过期不等于对方死了

**场景**：承接 §3.4。租约的作用是「worker 死了，别人能接手」。但如果 worker 没死，只是慢呢？

```
10:00  worker A claim dl_42（租约到 10:05），调用 submit_offline
       ……A 的请求卡住，A 还活着……
10:05  租约过期
10:06  回收 dl_42 → find_existing：A 的请求还没到 OpenList → 没找到
       → worker B 重新提交成功，写 running，引用 refB
10:07  A 的请求终于返回成功，A 照常写 running，引用 refA   ← 覆盖了 refB
```

结果：云端两个任务，PG 只跟踪 refA，refB 成了孤儿。A 没做错任何事——从它的视角看，锁一直在
自己手里。**分布式系统里，「我仍持有锁」无法被持续确认。**

**设计**（spec §6.5 第 1–3 步）：

1. **每次 claim 生成新的 `lease_owner`**（相当于 fencing token：「我是第几任持有者」）。
2. **写回时再验证一次**：

   ```sql
   SELECT … FROM anime_downloads WHERE id = 42 FOR UPDATE;
   -- 仅当 status = 'submitting' AND lease_owner = :mine 才写回
   ```

   A 的写回校验失败，什么都不改，记日志并告警，让人核对是否多了一个云端任务。
3. **租约必须大于调用超时**：租约 300 秒，调用超时 30 秒，并且配置校验不满足就拒绝启动。
   这让 A 正常情况下一定在租约过期前拿到结果，fencing 只防进程被冻结之类的极端情况。

第 3 步大幅降低发生概率，第 2 步保证即使发生也不会写坏数据。两者缺一不可。

项目里已有同样的实现：

- `app/services/avatars/processing.py`：写回前校验 `lease_owner == owner`，不成立时还为已上传的
  对象建删除补偿。
- `app/services/email/outbox.py`：`_owned_outbox` 同时校验 `locked_by` 与 `locked_until`。

**为什么不用 `attempt_count` 当 token**：`downloads retry` 会把它清零，编号可能重复，fencing 就失效了。
token 必须单调或唯一。

**原则**：锁和租约只能减少冲突，不能保证互斥。真正的保护在写入那一刻——带上「我是谁」的条件
再验证一次。

### 3.6 用版本号让重复执行收敛

**场景**：下载提交后，`check_download` 按自适应间隔查询云端进度（spec §7.4）。每次查到「还没完」，
就写下一次检查时间 `next_check_at`，并投递一条延迟执行的消息，形成一条**检查链**。

问题：同一行可能同时存在两条链。比如原消息只是迟到，兜底扫描已经补投了一条；两条链各自续约，
每 10 秒查两次，**永远持续下去**。更糟的是两条链可能同时发现完成，各发一次通知。

**设计**：`next_check_at` 兼作版本号，所有写回都带条件：

```sql
UPDATE anime_downloads SET next_check_at = :new
WHERE id = :id AND status = 'running' AND next_check_at = :observed;
-- :observed 是本次检查开始时读到的值
```

- 影响 1 行：本链胜出，继续投递下一条消息。
- 影响 0 行：别的链已经推进过，本链直接结束。

每一步只有一条链能前进，多余的链在下一步自然消亡。完成时的写回同样带这个条件，所以只会产生
一次完成通知。这就是**乐观并发控制（optimistic concurrency control）**：不加锁，靠「写的时候
值还是我读到的那个」来检测冲突。

和 §3.5 的区别：

| | fencing（§3.5） | 版本号（§3.6） |
|---|---|---|
| 防什么 | 失去所有权的写者覆盖新数据 | 多个等价执行者重复推进 |
| 有没有「持有者」 | 有，claim 时确定 | 没有，谁先写成功算谁 |
| 适用 | 有不可逆副作用的步骤（提交） | 只读外部调用 + 本地推进（检查） |

`check_download` 不需要租约：它对外部只做查询，重复查询无害，只需保证本地状态只被推进一次。

**原则**：重复执行无法杜绝时，让它变得无害——用条件写把「谁推进状态」收敛到唯一一方。

### 3.7 至少一次，还是至多一次

**场景**：发 Telegram 通知（spec §6.5 末段、§7.6）。

| 写法 | 崩溃窗口 | 结果 |
|---|---|---|
| A：发送 → 成功后标记 `sent` | 已发送、未标记 | 恢复后重发，手机收到两条 |
| B：先标记 `sent` → 再发送 | 已标记、未发送 | 永远不会再发 |

Telegram 不参与 PG 事务，也不提供去重键，**恰好一次在物理上做不到**。只能选：

- **至少一次**（at-least-once）：可能重复，不会丢；
- **至多一次**（at-most-once）：不会重复，可能丢。

怎么选，看哪种错误更贵：

| 动作 | 重复的代价 | 丢失的代价 | 选择 |
|---|---|---|---|
| 完成通知 | 多一条消息 | 错过更新 | 至少一次，不额外投入 |
| 离线下载 | 多一份文件、占配额 | 漏下一集 | 至少一次，**并且**用对账（§3.4）把重复压到最低 |
| 健康告警 | 多一条告警 | 不知道系统坏了 | 至少一次，且不设放弃上限 |

**一个「不小心变成至多一次」的真实例子**：初稿的健康告警（spec §7.7 修订前）。

```
宿主机网络故障
health_check：OpenList 不可达 → 写入 status=down → 发告警 → Telegram 也不可达（同一次故障！）
6 小时后：status 已经是 down，「没有变化」→ 不再告警
结果：这次故障的告警永远发不出去
```

「只在状态变化时告警」没错，错在把「状态改了」等同于「告警发了」。而且故障往往是**相关的**：
让 OpenList 挂掉的网络问题，同样让告警发不出去——告警最容易丢的时候，正是最需要它的时候。

修订后的设计：`status` 与 `alerted_status` 分开记录，只要两者不同就持续补发（spec §7.7）。
这就是把 §3.3 的 outbox 思路用在告警上。

**原则**：先明确每个副作用要的是哪种语义；凡是想要「至少一次」的，都要单独记录副作用是否完成，
否则你以为是至少一次，实际是至多一次。

## 4. 什么时候不需要这些机制

每一处保护都有成本：代码、测试、理解负担。判断标准是**写错了能不能自愈**，以及错误的代价。

| 场景 | 不加保护的最坏后果 | 能否自愈 | 决定 |
|---|---|---|---|
| `anime_feeds` 拉取租约不做 fencing（spec §7.1） | 多拉一次 RSS；ETag 被旧值覆盖导致下次拿到 200 而非 304 | 能：入库幂等，下次拉取自动修正 | 不加 |
| `episode_dedupe` 先查后插（spec §7.2） | 偶尔同一集下两个字幕组的版本 | 不能，但代价只是一份文件 | 接受，不加锁 |
| 短暂故障在告警发出前恢复（spec §7.7） | 少一条「坏了 / 好了」的告警 | 无所谓：系统已经好了 | 不补发 |
| 提交下载不做 fencing | 云端多出无人跟踪的任务 | 不能：外部世界的副作用无法撤销 | **必须加** |

对比第一行和最后一行：同样是「迟到的写回」，一个只浪费一次 HTTP 请求，一个在外部世界留下
无法撤销的痕迹。保护应该加在后者。

两个补充：

- **加了不必要的保护也有代价**：读代码的人会以为这里存在一个其实不存在的风险，从而误判系统的
  脆弱点。
- **规模影响取舍**：这是单用户、并发 2 的个人工具，所以接受了几处「极少数重复」。同样的设计
  放到多用户、高并发的生产系统，`episode_dedupe` 可能就值得用 advisory lock 保护。

## 5. 设计是怎么变好的：一次复盘

### 5.1 找缺口的方法

spec 在 §13 写了验收承诺（如「只产生一个下载任务和一条完成通知」「OpenList 停机期间发出一次告警」）。
找缺口就是**拿承诺逐条对照机制**：沿 §2.2 的方法问每对相邻步骤会怎样，结果违背了哪条承诺，
哪里就是缺口。

### 5.2 初稿的缺口与修复

| 缺口 | 违背的承诺 | 触发条件 | 修复（spec 位置） |
|---|---|---|---|
| 租约没有 fencing | 不重复提交 | 慢调用 | `lease_owner` + 租约 > 超时（§6.5） |
| `find_existing` 能否查到未验证 | 不重复提交 | 崩溃 | 新增 S0-6，预设降级路径（§6.5、§13） |
| 云端任务消失被当作失败 | 收到完成通知 | **正常运行** | `not_found` 状态 + 目录兜底（§5.1、§7.4） |
| `episode_dedupe` 措辞有歧义 | — | 正常运行 | 穷举阻挡状态（§7.2） |
| 告警丢失 | 停机时发出告警 | 相关性故障 | `alerted_status` 持续补发（§7.7） |
| 检查链重复 | 一条完成通知 | 消息迟到 + 补投 | `next_check_at` 条件写（§7.4） |

### 5.3 排优先级

1. **先看触发条件**：只在故障时触发的缺口，概率取决于故障频率；**在正常路径上触发**的缺口
   （如云端任务消失）会被反复碰到，优先级最高。
2. **再看代价能否自愈**：同 §4。
3. **再看修复成本**：fencing 只是几行代码，即使概率低也值得做。

### 5.4 有些问题不靠代码解决

「对账能否查到」「云端任务会不会被清理」「OpenList 状态刷新多快」都是关于外部系统的**事实**，
不是设计选择。正确做法是在实现前用 S0 技术验证测出来，并且**提前写好每种结果对应的路径**，
这样验证结果不会卡住实现，也不会在上线后才发现前提不成立。

还有一类缺口根本不是一致性问题，而是需求没定义清楚：`episode_dedupe` 的「非终态失败」可以读出
两种意思，决定了「A 组第 5 集失败后，B 组第 5 集要不要下」。这类问题实现者无法自行判断，
必须在 spec 阶段问清。

### 5.5 为什么在 spec 阶段做

现在改是改几行字；代码写完、跑了一段时间再发现，就要改状态机、做数据迁移、清理已经产生的
重复数据。

## 6. 数字是怎么来的

### 6.1 自适应检查间隔（spec §7.4）

已知：PikPak 对新番资源大多 10 秒内完成，绝大多数 30 秒内完成，少数会卡很久。

| 固定间隔 | 问题 |
|---|---|
| 5 分钟 | 10 秒下完的番，要等几分钟才通知 |
| 10 秒 | 卡住的任务 24 小时里被查约 8600 次；对非官方接口有限流风险 |

于是按提交后经过的时间前密后疏：0–2 分钟每 10 秒，2–10 分钟每 30 秒，10–60 分钟每 2 分钟，
之后每 10 分钟。常见情况 10–20 秒发出通知；卡满 24 小时也只查约 190 次。

**分布决定策略**：先弄清楚事件的时间分布，再让探测频率贴合它。

### 6.2 两个必须满足的不等式

- **租约 > 外部调用超时 + 余量**（300 > 30 + 60）：否则 fencing 从「极端情况的保险」变成
  「每次慢调用都触发」（§3.5）。
- **最大检查间隔 < broker 的 visibility timeout**（10 分钟 < 1 小时）：Redis broker 下延迟消息由
  worker 预取后在内存中等待；延迟超过 visibility timeout 会被判定为超时并重复投递。

参数之间的约束关系要写下来，最好在启动时校验，否则某次「只改一个参数」就会悄悄破坏正确性。

### 6.3 优化前先找瓶颈

端到端延迟 = RSS 拉取间隔（10 分钟） + 蜜柑自身更新延迟 + PikPak 下载（10–30 秒）
+ 检查间隔（10 秒）。把检查从 5 分钟降到 10 秒很值，但再往下降没有意义——大头在拉取间隔。

## 7. 速查清单

设计任何新的后台任务时逐条过一遍：

- [ ] **事实源**：任务的存在与进度只看 PG 吗？
- [ ] **消息丢失**：每一种唤醒消息背后，都有周期扫描兜底吗？（§3.1）
- [ ] **投递顺序**：消息是在事务提交**之后**才投递的吗？（§3.1）
- [ ] **先查后插**：有没有「查一下再插入 / 更新」？能换成唯一约束或条件写吗？（§3.2）
- [ ] **事实与义务**：状态变化带来的副作用，是在同一事务里记成「待完成」的吗？（§3.3）
- [ ] **不知道**：外部调用超时或崩溃时，恢复后怎么判断上次做没做？有对账手段吗？（§3.4）
- [ ] **所有权**：拿租约做不可逆的事，写回前验证所有权了吗？租约大于调用超时吗？（§3.5）
- [ ] **重复执行**：同一步可能被执行两次时，有条件写保证只推进一次吗？（§3.6）
- [ ] **语义**：每个副作用要的是至少一次还是至多一次？是否单独记录了「已完成」？（§3.7）
- [ ] **三问**：重试几次？怎么退避？死了落到哪？（`background-tasks.md` §4）
- [ ] **相称**：这处保护防的后果能自愈吗？成本与代价相称吗？（§4）
- [ ] **外部事实**：设计依赖的外部系统行为验证过吗？每种结果都有对应路径吗？（§5.4）

## 8. 自测题

<details>
<summary>1. 为什么不能先投递 Celery 消息、再提交 PG 事务？</summary>

worker 可能在事务提交前就收到消息，查不到行而丢弃；之后事务提交，这一行再也没人处理（除非有
兜底扫描）。另外如果事务回滚，消息却已经发出，worker 会处理一个不存在的任务。见 §3.1。
</details>

<details>
<summary>2. 两个 worker 同时 <code>INSERT … ON CONFLICT DO NOTHING</code> 同一个 infohash，会发生什么？</summary>

后到的插入会等先到的事务结束。先到的提交后，后到的发现冲突，什么都不做、影响 0 行。只有影响
1 行的一方投递唤醒消息。见 §3.2。
</details>

<details>
<summary>3. 如果把 <code>completed</code> 和 <code>notify_status=pending</code> 分成两次提交，会出什么问题？</summary>

取决于顺序：先写 `completed`，崩溃后 `notify_status` 停在 `none`，兜底不会扫到，通知永远不发；
先写 `notify_status`，崩溃后会发出「已完成」的通知，但下载其实没完成。见 §3.3。
</details>

<details>
<summary>4. <code>submitting</code> 状态存在的意义是什么？没有它会怎样？</summary>

它表达「已经动手，结果未知」。没有它，就只能在「提交前写 running」和「提交后写 running」之间选，
前者崩溃后库里说在下、云端什么都没有，后者崩溃后会重复提交。有了它，恢复时知道「这一行可能
提交过」，于是先对账再决定是否重提。见 §3.4。
</details>

<details>
<summary>5. 租约已经保证了同一时刻只有一个持有者，为什么还需要 fencing？</summary>

租约只保证「在租约有效期内」不会有第二个持有者。持有者变慢、租约过期后，它自己并不知道，
仍会照常写回，覆盖新持有者的结果。fencing 在写回那一刻再验证一次所有权。见 §3.5。
</details>

<details>
<summary>6. 为什么 <code>anime_feeds</code> 不需要 <code>lease_owner</code>，而 <code>anime_downloads</code> 需要？</summary>

拉取订阅源迟到写回的最坏后果是多拉一次 RSS，入库幂等，能自愈；提交下载迟到写回会让云端多出
一个无人跟踪的任务，外部副作用无法撤销。保护加在不能自愈的地方。见 §4。
</details>

<details>
<summary>7. <code>check_download</code> 为什么不用租约，而用 <code>next_check_at</code> 条件写？</summary>

检查对外部只做查询，重复查询无害，不需要「独占执行」；需要保证的只是本地状态只被推进一次，
以及重复的检查链能自然终止。条件写（乐观并发控制）正好满足，且比租约简单。见 §3.6。
</details>

<details>
<summary>8. 初稿的健康告警为什么会丢？修复的核心是什么？</summary>

初稿把「状态已改」等同于「告警已发」。故障往往相关：让 OpenList 不可达的网络问题，也让告警发不
出去；状态已改成 down，之后不再变化，就不会再发。修复是把「告警是否已发出」（`alerted_status`）
单独记录，两者不同就持续补发。见 §3.7。
</details>

## 9. 术语表与延伸阅读

### 术语

| 中文 | 英文 | 一句话 |
|---|---|---|
| 最终一致性 | eventual consistency | 不保证每一刻都一致，但保证最终收敛到一致 |
| 事实源 | source of truth | 判断「真实状态」时唯一相信的地方 |
| 唤醒信号 | wakeup signal | 只加速、可丢失的「有活了」提示 |
| 幂等 | idempotent | 执行一次和执行多次效果相同 |
| 先查后插竞态 | check-then-act race | 检查与写入之间被别人插入 |
| 事务性发件箱 | transactional outbox | 在业务事务里记下「待发出的副作用」 |
| 对账 | reconciliation | 本地状态不确定时，查询外部系统的事实来补全 |
| 租约 | lease | 带过期时间的锁，持有者死后可被回收 |
| 栅栏令牌 | fencing token | 写入时校验「我仍是当前持有者」的标识 |
| 乐观并发控制 | optimistic concurrency control | 不加锁，写入时检查值是否被改过 |
| 至少一次 / 至多一次 | at-least-once / at-most-once | 可能重复不丢 / 可能丢不重复 |
| 幂等键 | idempotency key | 远程接口据此识别重复请求，只执行一次 |
| 可见性超时 | visibility timeout | 消息被取走后多久未确认就重新投递 |

### 延伸阅读

  第 11 章「流处理」。
- Stripe 工程博客关于 `Idempotency-Key` 的设计：远程接口如何自带幂等。
- Chris Richardson，microservices.io 上的 *Transactional outbox* 模式。
