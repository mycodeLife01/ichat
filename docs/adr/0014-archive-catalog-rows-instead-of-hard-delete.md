# 模型目录以归档代替物理删除，Run 按快照路由解析凭据

聊天模型、模型路由、模型上游只能归档，不能物理删除：三张表各有 `archived_at`，归档行永不删除，凭据始终可解密。归档项从可用目录中消失，也不能被编辑或启停，只能通过显式恢复回到目录。自然 key 的唯一约束收窄为只覆盖未归档行的部分唯一索引，因此归档后可以用同一个 key 新建；管理面改用行句柄 `ref`（`model-12` / `upstream-4` / `route-31`）寻址具体行，归档项只能按 `ref` 恢复。

同一个 key 可能同时对应一条活跃行和多条归档行后，按 upstream key 回查凭据不再唯一。Run 执行因此改为 `runs.model_config_snapshot.route_id → model_routes → model_upstreams`，不看 `archived_at`；快照中的 upstream key 只作一致性校验。v1 与 v2 快照都必含 `route_id`，不需要回填或新快照版本。

归档语义对齐原有外键：归档模型在同一事务内级联归档其未归档路由，路由写入与模型相同的 `archived_at`；恢复模型只恢复这一批路由中上游仍活跃的部分。归档上游要求没有任何未归档路由引用它，否则冲突（409）并列出阻塞路由。恢复要求同 key（或同路由三元组）没有活跃行，路由恢复还要求父模型与父上游都活跃。

该决策依赖三条不变量：

1. 目录行永不删除，只归档。
2. `route.upstream_id` 不可变（路由三元组不可改名）。
3. 活跃路由的父模型与父上游必然都活跃。

本 ADR 取代 `docs/handover/2026-08-29-database-model-catalog.md` 与 `docs/architecture/frontend.md` 中「Web 与 CLI 都不提供 hard delete」的表述：仍然没有 hard delete，但新增了可逆的归档。

## 考虑过的替代方案

- 物理删除加 `ON DELETE RESTRICT`：删除上游会让引用它的在途 Run 找不到凭据而失败，这正是原决策禁止 hard delete 的原因。
- 归档但保留 key 占用：行为安全，但"归档后重建同名"会失败，与运维直觉相反。
- 继续按 upstream key 回查，查询时"活跃行优先、否则回退归档行"，并在归档上游前检查未完成 Run：需要额外的排序约定和前置检查，且检查与 Run 创建之间存在并发窗口；按 `route_id` 解析在结构上消除了这些问题。
- 从上游侧级联归档路由：路由从属于模型，从上游侧级联会静默删掉若干模型的可用路径，应由管理员显式处理。

## 后果

在途 Run 不受归档或同名重建影响，始终使用快照当时那一行上游的凭据；同一上游行原地轮换 API key 仍立即生效。归档不能用来中止在途 Run，中止需要取消 Run，与"下线"一致。归档行只读，其凭据在归档后冻结。回滚到不识别 `archived_at` 的旧代码时，归档行会重新出现在目录中；若已发生同名重建，旧代码按 key 查询结果不确定，回滚前需要让每个 key 只剩一行。
