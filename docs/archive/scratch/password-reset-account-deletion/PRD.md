# 密码重置与账户注销（邮箱验证）

Type: feature
Status: ready-for-agent
Blocked by: None

日期：2026-07-13
需求来源：本分支 grilling 设计会话（基于 `feat/email-verification` 已交付的认证邮件基础设施）
术语依据：根目录 `CONTEXT.md`（认证令牌 / 邮箱验证 / 密码重置 / 改密 / 注销 / 停用）

## Problem Statement

用户当前一旦忘记密码就永久失去账户——产品没有任何自救通道。已登录用户也无法修改密码（怀疑密码泄露时无计可施），更没有办法主动终止自己的账户。对一个存储用户对话数据的产品，这三个账户生命周期能力的缺失既是体验缺口也是信任缺口。

## Solution

在现有认证邮件基础设施（通用认证令牌表、邮件 outbox、Redis 限流/冷却）之上补齐三个能力：

1. **密码重置**：匿名用户提交邮箱，收到含 30 分钟有效链接的邮件，凭链接设置新密码。
2. **改密**：已登录用户凭当前密码直接设置新密码，不走邮件。
3. **注销**：已登录用户重输密码发起注销，收到确认邮件，点击链接后账户立即停用（软注销，数据保留，物理清除留待后续迭代）。

任何密码变更或注销生效都会吊销该用户的全部登录凭证与挂起的敏感操作令牌。

## User Stories

1. 作为忘记密码的用户，我想在登录页提交我的邮箱申请重置，以便重新获得账户访问权。
2. 作为申请重置的用户，我想收到一封品牌化的重置邮件，内含 30 分钟有效的一次性链接，以便安全地设置新密码。
3. 作为点击重置链接的用户，我想提交新密码后立即生效，以便用新密码登录。
4. 作为重置了密码的用户，我希望所有旧登录会话被强制下线，以便确认可能持有旧凭证的攻击者被清出。
5. 作为邮箱尚未验证的用户，我也想使用忘记密码功能，以便不因未验证而被永久锁死。
6. 作为通过重置链接证明了邮箱所有权的用户，我希望系统顺带将我的邮箱标记为已验证，以便不必再单独点验证邮件。
7. 作为注重隐私的用户，我希望任何人输入我的邮箱申请重置时，无法从响应中判断该邮箱是否注册过，以便我的注册状态不被探测。
8. 作为误输了未注册邮箱的用户，我想看到与成功场景一致的「如果该邮箱已注册，重置邮件已发送」提示，以便不泄露信息的同时获得下一步指引。
9. 作为收到过期重置链接的用户，我想得到明确的「链接无效或已过期」报错，以便知道需要重新申请。
10. 作为重复点击同一重置链接的用户，我想在第二次得到失效提示，以便确认链接是一次性的。
11. 作为已登录用户，我想凭当前密码修改密码，以便定期轮换或在怀疑泄露时立即止损。
12. 作为改密成功的用户，我希望包括其他设备在内的全部会话被强制重新登录，以便旧凭证立即作废。
13. 作为已登录用户，我想发起注销账户，以便终止我与产品的关系。
14. 作为发起注销的用户，我希望必须重输当前密码，以便他人拿到我未锁屏的设备时无法替我注销。
15. 作为发起注销的用户，我想收到一封确认邮件并点击链接才真正生效，以便误操作有反悔的机会。
16. 作为完成注销的用户，我希望账户立即停用——无法登录、无法刷新令牌、无法访问任何接口，以便确认注销已生效。
17. 作为完成注销的用户，我希望我挂起的所有敏感操作链接（重置、验证、注销）同时作废，以便不留下任何可被利用的凭证。
18. 作为注销后反悔的用户，我理解本期恢复需联系运维处理，以便在数据尚未物理清除时找回账户。
19. 作为已停用账户的前用户，我希望有人用我的邮箱申请密码重置时系统静默不发信，以便我不再收到打扰邮件。
20. 作为先发起注销又改了密码的用户，我希望之前那封未点击的注销确认邮件自动作废，以便密码变更后不存在遗留的危险链接。
21. 作为普通用户，我希望短时间内重复申请重置邮件会被冷却限制（60 秒），以便我的邮箱不被轰炸。
22. 作为平台运营者，我希望所有匿名端点有 IP 限流，以便脚本无法批量滥用发信和探测。
23. 作为平台运营者，我希望改密与发起注销的密码校验有严格限流，以便持有被盗会话的攻击者无法在线爆破密码。
24. 作为平台运营者，我希望 Redis 故障时忘记密码仍然可用（降级到数据库冷却），以便用户自救通道不因缓存故障而中断。
25. 作为平台运营者，我希望 Redis 故障时高熵令牌的消费不被阻塞（fail-open），而发起注销这类非紧急操作被拒绝（fail-closed），以便故障时的行为与风险等级匹配。
26. 作为运维人员，我希望重置与注销邮件走既有 outbox 通道（claim/lease/重试/dead），以便沿用现有的排查与补投手段。
27. 作为运维人员，我希望新令牌 TTL 与限流参数均为独立环境变量，以便按风险偏好调整而不影响验证邮件。
28. 作为后续迭代的开发者，我希望本期明确记录「注销 = 停用 + 数据保留」的决策与物理清除的待办，以便冷静期清除功能有清晰的接续点。

## Implementation Decisions

**新增五个认证端点**（均挂在既有 auth 路由前缀下，命名沿用扁平动宾 kebab-case 风格）：

| 端点 | 认证 | 行为 |
|---|---|---|
| `request-password-reset` | 匿名 | 恒定 200 防枚举；仅存在且未停用的邮箱真正签发令牌并入 outbox |
| `reset-password` | 匿名 | 消费令牌 + 设新密码 |
| `change-password` | 登录态 | 校验当前密码后设新密码 |
| `request-account-deletion` | 登录态 | 重输密码（sudo mode）通过后发确认邮件 |
| `confirm-account-deletion` | 匿名 | 消费令牌，账户停用 |

- 三个命令端点统一返回既有的命令状态响应模型，不自动登录（未来升级返回登录凭证是向后兼容的）。
- 请求模型复用既有校验：密码 8–128 字符；令牌 43 位 urlsafe 模式。

**令牌服务泛化**：既有令牌签发/消费函数从硬编码「邮箱验证」用途泛化为按 purpose 参数化，新增 `password_reset` 与 `account_deletion` 两个用途。通用认证令牌表结构不变（partial unique index 已保证同用户同用途仅一个 active 令牌）。

**注销语义（本期）**：软注销——确认后置停用标志 + 吊销全部 refresh token + 撤销该用户所有用途的 active 认证令牌。数据保留；物理清除（冷静期 + 周期任务）明确留作后续迭代。既有的「停用用户被 login / refresh / 当前用户依赖拒绝」机制即为注销的执行面，无需新增访问控制。

**交叉作废矩阵**：

| 触发事件 | 撤销范围 |
|---|---|
| 重置密码成功 / 改密成功 | 全部 refresh token + 该用户 active 的 `password_reset` 与 `account_deletion` 令牌 |
| 确认注销成功 | 全部 refresh token + 该用户所有用途的 active 令牌 |
| 签发任一用途新令牌 | 同用途旧 active 令牌（既有语义不变） |

**邮箱验证不变量扩展**：重置密码成功且令牌的收件邮箱等于用户当前邮箱时，顺带置邮箱已验证。不变量从「验证邮件」收窄的表述扩展为「任何 TTL 内成功消费的、发往当前邮箱的认证令牌都构成一次邮箱验证」（已写入 CONTEXT.md）。

**限流与 Redis 故障策略**（对号入座既有三种模式）：

| 端点 | 模式 |
|---|---|
| request-password-reset | 同 register：IP 限流 fail-open + 邮箱冷却，Redis 故障降级为数据库冷却 |
| reset-password / confirm-account-deletion | 同 verify：IP 限流，fail-open |
| request-account-deletion | 同 resend：fail-closed + 用户/邮箱冷却 + IP 限流 |
| change-password | 用户维度失败尝试限流 + IP 限流，fail-closed（防在线爆破，无邮件冷却） |

邮箱冷却复用 60 秒参数，但按 purpose 独立计数，不与验证邮件互相挤占。恒定响应要求：不存在的邮箱同样占用冷却 key，避免 429 出现与否泄露注册状态。

**新配置**：密码重置令牌 TTL（默认 1800 秒）、注销令牌 TTL（默认 1800 秒）各自独立环境变量；三组新端点限流参数。

**邮件**：新增重置密码与注销确认两个模板，复用既有品牌化 HTML 卡片渲染器与 outbox 投递通道；注销确认邮件含「如非本人操作请立即修改密码」提示。

**ADR**：「注销 = 软停用 + 延后物理清除」满足难逆、反直觉、真实权衡三条件，实现时随附 ADR。

## Testing Decisions

- 好测试只断言外部行为：HTTP 状态码与响应体、数据库可观测状态（用户停用标志、令牌 used/revoked、outbox 行）、捕获到的 Celery 入队，而非内部函数调用轨迹。
- **主缝（最高层，复用既有模式）**：HTTP API 层——ASGI 测试客户端 + 真实 PostgreSQL + fakeredis + 捕获 Celery enqueue。先例：既有邮箱验证 API 测试套件。在此层覆盖：恒定响应防枚举（存在/不存在/已停用邮箱响应一致）、令牌消费/过期/重复使用、交叉作废矩阵、软注销后登录/刷新/取当前用户全被拒、各端点限流与 Redis 故障降级行为、重置顺带置邮箱已验证。
- **辅缝（既有单元缝扩展，不新增缝）**：令牌服务按 purpose 泛化的单元测试扩展既有令牌服务测试；两个新邮件模板扩展既有渲染器测试。
- 不引入任何新测试缝。运行后端测试前须停掉 LLM worker 与 celery-worker 容器（避免抢占测试数据，见项目既有约定）。

## Out of Scope

- **前端**：重置落地页、注销确认落地页、登录页入口、设置区表单均单独一期。上线节奏须保证前端就位前不产生死链触达（匿名接口存在但前端无入口）。
- **物理数据清除**：冷静期、周期清除任务、注销后自助恢复均留待后续迭代。
- **自动登录**：重置成功后返回登录凭证。
- **改邮箱流程**、Postmark bounce/delivery webhook、防重复发送（at-least-once 语义维持现状）。

## Further Notes

- 部署时需在生产 `.env` 增加新环境变量并 force-recreate api / celery-worker / celery-beat（restart 不重载 env）。
- 已停用账户申请重置的外部表现与不存在的邮箱完全一致（静默不发信）；将来若做「冷静期内恢复账户」，须设计显式恢复入口，不借道密码重置。
- Redis 降级时数据库冷却只能覆盖已有令牌记录的邮箱，不存在的邮箱在降级期间无冷却——响应恒定，仅发信侧无影响，风险可接受。
