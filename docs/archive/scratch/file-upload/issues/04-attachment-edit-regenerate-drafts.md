# 附件编辑、替换、重新生成与草稿恢复

## 目标

补齐消息修订和 composer 恢复语义，使附件在编辑、移除、排序、刷新和重新生成时都有
确定行为，并为后续 30 天 detached 回收留下准确事实。

## 交付范围

1. 编辑消息时，省略 `attachment_ids` 表示继承当前修订的附件；显式列表表示完整替换；
   空列表表示全部移除。后端必须区分“字段缺失”和“空数组”。
2. 重新生成固定复用原用户消息修订的附件，不读取 composer 当前草稿，也不允许调用方
   偷换 attachment IDs。
3. MessageAttachment 保存稳定顺序与分享所需元数据。离开所有当前消息修订引用的文件
   标记 `detached_at`；再次由合法修订引用时取消 detached。归档消息保留元数据，旧
   transcript 保持不可变。
4. 自动标题输入改为用户实际文字、附件安全元数据和首条助手回复，禁止再次注入完整附件
   派生正文。
5. 前端编辑器可继承、移除、替换和重排附件；刷新恢复按用户+会话保存的文字、upload/file
   IDs 和顺序。登出或切换账号清除本地草稿；页面关闭不能被当成可靠 cancel。
6. 所有编辑路径继续执行所有权、ready、purpose、有效期、数量、总大小和 token 预算验证，
   并与新 Message/Run 原子提交。

## 验收

- 省略、显式替换、空列表和 regenerate 四类语义均有 API 集成测试和前端交互测试。
- 移除最后一个模型可消费附件且文字为空时拒绝发送；失败不会改变原修订或 detached 状态。
- 附件顺序在草稿、消息、transcript 和重新生成中稳定；并发编辑不产生错误引用。
- 自动标题测试证明只收到安全元数据而非文档正文。
- 刷新、页面隐藏、登出和账号切换场景可复现，且不会错误取消后端 queued/processing 上传。
- 后端和前端全套检查通过。
