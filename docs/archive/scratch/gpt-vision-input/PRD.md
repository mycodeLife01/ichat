# GPT 视觉输入与图像上下文约束

Type: feature
Status: ready-for-human
Blocked by: None

日期：2026-08-02
需求来源：文件上传功能完成后的 GPT 视觉理解设计确认会话
术语依据：项目领域词汇表中的内容块、图像块、历史仅展示图片、视觉输入模型、视觉依赖会话、图片上下文状态、安全图像派生物和模型图像读取许可
相关决策：ADR 0006–0009

## Problem Statement

iChat 已经支持统一文件上传，但图片进入 Run transcript 时统一表示为模型不可读取的附件提示。因此即使用户选择官方支持图片输入的 GPT 模型，模型也拿不到图片内容；产品只能展示图片，无法回答图片中的物体、文字、图表或视觉关系。

系统同时接入 DeepSeek 与 GPT。DeepSeek 当前不支持图片输入，而 GPT 目录中只有部分明确验证过的模型支持图片。如果继续把图片上传能力与模型能力分离，用户可能在 DeepSeek 下花费时间上传图片，随后才发现模型没有读取；如果在已有图片历史中任意切换模型，又可能出现部分 Run 看过图片、部分 Run 只收到附件提示，但界面无法解释真实上下文的情况。

视觉功能上线前已经存在由 DeepSeek 处理的图片消息。这些旧 Run 的 transcript 只包含 `AttachmentNoticeBlock`。系统不能静默重写旧 transcript，也不能在用户普通切换 GPT 时假装 GPT 自动获得了过去从未进入模型输入的图片；但用户仍需要一条明确路径，从某条旧图片消息重新生成或编辑，使新的 GPT Run 真正读取图片。

图片历史还带来短期 URL、上下文预算、隐私边界和存储权限问题。把预签名 URL 固化进 transcript 会导致用户很久后返回时 URL 已过期；把原件直接交给 LLM Worker 会扩大凭证泄露面；把解析失败静默降级为纯文字则会再次制造“用户以为模型看过图片”的错误事实。

## Solution

为模型目录增加显式、模型级的图片输入能力白名单。首个生产视觉模型为 `gpt-5-mini`；只有明确配置并完成真实冒烟验证的模型才能消费 `ImageBlock`。DeepSeek 下选择、粘贴或拖入图片时不创建上传，而是让用户切换到视觉模型；文档上传继续可用。

当当前有效消息分支包含 `ImageBlock` 时，会话成为视觉依赖会话，后续 Run 必须使用视觉输入模型。该状态从当前消息与其有效 Run transcript 派生，不新增容易漂移的会话级模型字段或视觉标记。编辑移除全部图片、或编辑较早消息归档后续图片分支后，约束可以自然解除。

视觉功能上线前的历史仅展示图片保持旧 Run 不变。普通发送仍可继续使用 DeepSeek，但不能直接切换 GPT；用户可以从当前分支最早的历史仅展示图片开始编辑或重新生成。新的 GPT Run 为该锚定消息生成 `ImageBlock`，更新消息的当前 Run 引用，并按既有分支语义归档后续消息。这样既不篡改历史，又避免更早 notice 与较晚 `ImageBlock` 形成无法选择模型的混合上下文。

GPT 只接收现有图片安全 preview：完整解码、转为 WebP、质量 82、去除元数据，动画只发送首帧。`ImageBlock` 保存模型所见派生物的稳定快照，不保存对象存储地址或临时 URL。每次 Model Call——包括 tool loop 后续调用、provider 重试和用户很久后返回产生的新 Run——都通过窄图片解析接口重新校验并签发五分钟 URL。

安全 preview 迁入独立私有 bucket。LLM Worker 只持有该 bucket 的读取/签名凭证，在基础设施权限层无法读取附件原件。视觉能力只有在 schema 切换、preview backfill、真实 R2 + GPT 冒烟测试和全部自动化检查完成后才开启；回滚只清空视觉白名单，不改写 transcript 或回迁对象。

## User Stories

1. 作为选择视觉 GPT 模型的用户，我想让模型真正读取上传图片，以便询问图片中的物体、文字、图表和视觉关系。
2. 作为只发送图片的用户，我想在没有文字时也能创建消息，以便直接让 GPT 理解图片。
3. 作为同时发送文字与图片的用户，我想让二者在同一用户 turn 中进入模型，以便问题与图片保持关联。
4. 作为同时发送图片和文档的用户，我想让附件按我的选择顺序进入上下文，以便“第一张图”和“后面的 PDF”具有稳定含义。
5. 作为连续追问图片的用户，我想在后续 turn 中继续引用先前图片，以便无需每次重新上传。
6. 作为很久后返回会话的用户，我想继续询问历史图片，以便旧的预签名 URL 过期不会破坏会话。
7. 作为使用工具型对话的用户，我想让每次 tool loop 后续模型调用仍能读取图片，以便工具调用不会丢失视觉上下文。
8. 作为遇到 provider 重试的用户，我想让重试使用新签名的图片 URL，以便短期许可不会导致无意义失败。
9. 作为关注隐私的用户，我希望 GPT 只接收去元数据的安全图片派生物，以便位置、设备和拍摄信息不会随原件发送给 provider。
10. 作为上传图片的用户，我希望下载功能仍返回原始字节，以便模型输入规范化不会覆盖我的原件。
11. 作为上传动画 WebP 的用户，我想明确知道模型只获得第一帧，以便不会误以为 GPT 看过完整动画。
12. 作为上传静态图片的用户，我希望模型获得稳定的高细节输入，以便同一功能不会因隐式 detail 策略变化而表现不一致。
13. 作为普通用户，我不希望每次发送图片都出现额外隐私确认或通知，以便视觉输入体验与普通聊天一致。
14. 作为选择 DeepSeek 的用户，我希望选择、粘贴或拖入图片时立即获知不支持，而不是上传结束后才失败。
15. 作为选择 DeepSeek 的用户，我希望系统在提示不支持图片前不创建任何上传，以便不浪费时间、流量和附件配额。
16. 作为在 DeepSeek 下选择纯图片的用户，我想一键切换到视觉 GPT 后继续，以便不必重新操作文件选择器。
17. 作为在 DeepSeek 下同时选择图片和文档的用户，我想选择切换 GPT 并上传全部，以便完整保留我的输入意图。
18. 作为在 DeepSeek 下同时选择图片和文档的用户，我想选择只上传文档，以便继续使用 DeepSeek 而不丢失可读文件。
19. 作为在 DeepSeek 下误选混合文件的用户，我想取消整个动作，以便系统不自动作出替我选择模型或文件的决定。
20. 作为在 GPT 草稿中已有图片的用户，我希望切换 DeepSeek 时保留草稿，以便误触模型选择不会丢失工作。
21. 作为在 GPT 草稿中已有图片的用户，我想选择继续使用 GPT，以便不必移除图片。
22. 作为确实要切换 DeepSeek 的用户，我想移除或取消全部图片上传后完成切换，同时保留文字和文档草稿。
23. 作为取消上传失败的用户，我希望待绑定文件期限最终回收资产，以便失败不会永久占用配额。
24. 作为只有文字或文档历史的 DeepSeek 用户，我想随时切换到视觉 GPT，以便首个模型不会永久锁定会话。
25. 作为视觉依赖会话的用户，我希望非视觉模型在模型选择器中被禁用，以便不会创建必然缺少图片的 Run。
26. 作为想在视觉依赖会话改用 DeepSeek 的用户，我想得到新建对话入口，以便能够明确放弃图片上下文。
27. 作为编辑消息并移除当前分支最后一张图片的用户，我想在同一次操作中选择 DeepSeek，以便约束随候选分支及时解除。
28. 作为编辑较早消息并归档后续图片分支的用户，我想在同一次操作中选择 DeepSeek，以便系统按操作后的真实分支判断能力。
29. 作为视觉功能上线前上传过图片的 DeepSeek 用户，我希望旧会话仍可继续使用 DeepSeek，以便升级不会突然封死既有会话。
30. 作为拥有历史仅展示图片的用户，我希望普通发送时不能直接切换 GPT，以便产品不会暗示 GPT 自动看到了旧图片。
31. 作为拥有历史仅展示图片的用户，我想从最早一条此类消息直接重新生成并选择 GPT，以便无需先编辑文字也能升级视觉输入。
32. 作为拥有历史仅展示图片的用户，我想编辑最早一条此类消息并选择 GPT，以便可以同时调整问题和升级图片输入。
33. 作为升级旧图片消息的用户，我希望新的 GPT Run 真正保存 `ImageBlock`，以便后续历史重放符合模型实际所见。
34. 作为查看旧 Run 的用户，我希望原 DeepSeek transcript 继续保留附件提示，以便审计事实不被视觉升级改写。
35. 作为升级旧图片消息的用户，我接受该消息之后的分支被归档，以便新回答不会与基于旧输入产生的后续对话混合。
36. 作为有多条历史仅展示图片的用户，我希望只能从最早一条开始升级，以便不会形成更早不可读图片与较晚可读图片混合的死锁。
37. 作为不愿归档旧分支的用户，我想新建对话并重新上传图片，以便保留原会话不变。
38. 作为视觉升级 Run 失败或被取消的用户，我希望会话仍诚实保持视觉依赖，以便系统不会悄悄回到旧的附件提示输入。
39. 作为重新生成图片消息的用户，我希望消息随后引用新的 Run 输入快照，以便未来重放不会继续采用旧 notice。
40. 作为返回旧会话的用户，我希望系统优先恢复该会话最近一次仍可用且兼容的 Run 模型，以便模型选择符合会话上下文。
41. 作为返回旧会话且原模型下线的用户，我希望系统回退到兼容的全局偏好，再回退到目录中第一个兼容模型，以便仍能继续聊天。
42. 作为用户，我不希望模型恢复过程弹出额外通知，以便回到会话时保持安静、可预测。
43. 作为没有可用视觉模型的视觉会话用户，我希望输入区变为只读而不是降级到 DeepSeek，以便不会产生不完整回答。
44. 作为没有可用视觉模型的用户，我仍想查看历史、下载附件、删除会话和新建对话，以便故障不会锁住其他数据操作。
45. 作为视觉能力恢复后的用户，我想继续原视觉会话，以便临时停用不造成永久损失。
46. 作为发送请求失败的用户，我想收到稳定机器错误码，以便前端能够给出正确恢复动作。

50. 作为历史仅展示图片中普通选择视觉模型的用户，我想得到指向最早升级锚点的明确恢复方式，以便知道该从哪里重新生成。

55. 作为发送多张图片的用户，我希望目标 turn 在创建 Run 前完成上下文预算校验，以便不会开始一个必然超限的生成。

## Implementation Decisions

### 产品与模型能力

- DeepSeek 不支持图片输入。用户在 DeepSeek 下选择、粘贴或拖入图片时，前端必须在创建上传前阻止；文档不受影响。
- 混合选择图片与文档时提供三个动作：`Switch to GPT and upload all`、`Upload documents only`、取消。选择仅文档时跳过图片并保持其余文件相对顺序。
- GPT 图片草稿切换 DeepSeek 时保留草稿；用户只能继续使用 GPT，或取消/移除全部图片后切换。文字与文档草稿保留，失败取消由既有待绑定期限兜底。
- 不增加图片发送通知、首次隐私提示或逐次确认。只有模型兼容性冲突才阻止操作。
- 视觉能力属于具体模型。使用 `OPENAI_VISION_MODELS` 显式配置，必须是 `OPENAI_MODELS` 的非空、无重复子集；DeepSeek 永远不能进入该白名单，未知模型默认关闭。
- 首个生产配置使用 `gpt-5-mini`。每个视觉白名单模型在目录中声明 `supports_image_input=true` 与正数 `image_token_reserve=8192`；非视觉模型分别为 false 与空值。
- 配置中出现空模型 ID、重复 ID、非子集或无有效 token 预留时，API 与 Worker 启动失败。不得根据 GPT 名称、OpenAI provider 或官方文档自动授予生产能力。
- capabilities 在每个模型条目返回 `supports_image_input`，删除错误表达全局能力的 `files.image_model_input`；token 预留属于服务端接纳策略，不向前端暴露。
- OpenAI 图片 wire 固定使用 `detail="high"`。首版不提供用户 detail 选项。

### 图片上下文与历史升级

- 图片上下文状态从当前未归档用户消息及其当前 Run transcript 派生，不新增 conversation-level 模型字段或视觉布尔值。
- 状态分为 `none`、`vision_required`、`legacy_upgrade_required`。前者无图片约束；第二种表示当前有效输入含 `ImageBlock`；第三种表示当前分支含旧图片附件，但当前输入只含 `AttachmentNoticeBlock`。
- 归档消息与脱离附件不参与状态计算。编辑操作按完成后的候选分支计算，因此移除最后一张图片或归档后续图片分支时可以在同一操作选择 DeepSeek。
- `vision_required` 状态只能使用视觉模型。没有可用视觉模型时输入区只读，但查看、下载、删除和新建对话保持可用；不得降级为文本模型。
- `legacy_upgrade_required` 的普通发送继续允许 DeepSeek，但禁止普通切换 GPT。用户可新建对话，或从当前分支最早的历史仅展示图片开始编辑/重新生成并选择 GPT。
- 历史升级只投影锚定用户消息，不批量升级其他旧图片；既有分支规则归档锚点之后的消息。有更早历史仅展示图片时禁止升级较晚图片。
- 新升级 Run 必须让原用户消息的当前 Run 引用指向新 Run。旧 Run 及其 notice transcript 保持不变。
- 新 Run 创建事务提交后，新的用户输入快照立即成为当前有效输入；即使 Run 后续失败或取消也不回退。
- 重新打开会话时，模型优先级依次是：最近一次仍在目录且满足当前约束的 Run 模型、满足约束的全局偏好、目录中第一个满足约束的模型。新对话仍优先全局偏好。

### 文件表示、schema 与 transcript

- 文件资产的 `model_consumable` 直接替换为 `model_input_kind`，取值为 `document`、`image` 或空值。它只描述安全模型输入表示是否存在，不混入具体模型能力。
- 按已确认的一步到位策略执行短维护窗口：停止 API、LLM Worker、file-worker 和相关任务；新增并回填 `model_input_kind`；删除旧字段；同版本发布所有后端与前端；旧浏览器标签页必须刷新，不提供兼容层。
- `file_objects` 增加 `model_preview_private` 存储位置。图片 preview 使用新位置，原件和文档派生物继续使用 canonical private 存储。
- 新增 provider-neutral `ImageBlock`。它保存文件身份、安全展示文件名，以及模型实际接收 preview 的媒体类型、SHA-256、宽度、高度、处理版本和警告；不保存 bucket、object key、原件哈希、图片字节或预签名 URL。
- `processor_version` 首版沿用现有 `image-v1`：它标识完整解码、首帧选择、RGBA 转换、WebP 质量 82 重编码和去元数据的算法契约；SHA-256 标识精确输出字节，两者不能互相替代。
- transcript 使用 `type=image` 严格序列化和反序列化全部图像字段。未知类型、缺字段或不一致视为 transcript 损坏，不静默忽略。
- 用户输入内容顺序固定为：非空文字在前，随后按请求附件 ID 顺序逐一产生 `DocumentBlock` 或 `ImageBlock`，不同附件类型不重新分组。纯图片消息在视觉模型下合法。
- 历史上下文重放所有仍被裁剪策略保留的图片 turn，不把图片限制为首个 Model Call 或首轮。
- 已完成 Run transcript 不可变；同一用户消息可由旧 DeepSeek Run 保存 notice，也可由后续 GPT Run 保存新的图像输入快照。

### Provider 投影与图片解析

- OpenAI user message 使用混合内容数组投影，不再把所有用户内容块压成单一字符串。
- 每张图片 wire 前后增加不可信图片附件边界，包含附件序号、安全文件名和动画仅首帧警告；图片 URL 位于边界内并固定使用 high detail。
- 基础 system prompt 删除“图片仅展示”的旧描述，明确实际提供的图片可以分析；同时声明图片中的文字、二维码和指令属于低信任用户数据，不能覆盖 system prompt。notice 继续表示模型未获得内容。
- DeepSeek adapter 对任何 `ImageBlock` fail-closed，即使上层校验遗漏也不能发起 provider 请求。
- agent kernel 定义窄、异步、批量的 `ImageInputResolver` 协议；files 服务实现数据库查询、快照校验与签名。OpenAI provider 只依赖协议，不读取 ORM、bucket 设置或存储凭证。
- 每次真正组装 Model Call 前，从裁剪后的上下文收集全部图像块，按文件 ID 去重，以一次查询读取文件资产和 preview 对象，整批校验生命周期、存储位置、媒体类型、哈希、尺寸和处理版本。
- 每个唯一图片在单次调用中只签发一个 URL，重复出现时复用；投影时恢复原始块顺序。
- 任一图片校验或签名失败，则整次调用失败且不向 provider 发送部分图片或纯文字上下文。
- 每次 Model Call、tool loop 后续调用和 provider 重试都重新解析并签发 URL。读取许可复用五分钟 TTL，因此用户长时间离开后返回不受旧 URL 影响。
- 不使用 provider Files API，不把图片 Base64 固化进 transcript，也不让最多 50 MiB 的附件常驻扩张 Worker 请求体。

### 预算、失败与重试

- 每个 `ImageBlock` 按所选模型的 8,192 token 预留量参与估算；该值是保守接纳预算，不是 provider 计费承诺。
- 当前目标 turn 的文字、完整文档和全部图片预留共同校验。超限时在创建 Run 前使用既有 413 语义拒绝，不截断图片或文档。
- 历史按完整 turn 裁剪；保留 turn 时保留其全部文字、附件与回答。视觉依赖状态基于当前有效分支，不因某张旧图在单次调用中被预算裁掉而解除。
- 现有图片与消息限制不变：单图最多 10 MiB、最长边 8,192、总像素最多 20,000,000；每条消息最多五个附件，原件合计最多 50 MiB。
- preview 缺失、位置错误、哈希/尺寸/版本不匹配时，Run 以稳定的 `image_input_unavailable` 类别失败，不重试、不转换为 notice。
- 暂时数据库、存储或签名故障仅在 provider 尚未产生任何输出时按既有 executor 边界重试；provider 无法拉取 URL 时重试必须重新签名。
- 异常持久化与日志先提取稳定错误类别和安全消息，不保存可能包含 URL 或请求体的原始异常对象。

### 服务端权威校验与 API 合同

- 四个入口必须执行相同的服务端权威校验：创建会话并发送首条消息、现有会话继续发送、编辑并重新生成、重新生成历史消息。
- 校验在持有会话行锁的事务中执行，并以操作完成后的候选消息分支为准。失败必须发生在归档消息、绑定附件和创建 Run 之前。
- 应用错误 envelope 保留既有 `detail`，新增可选稳定 `code`。应用提示使用英文，前端只按 code 决定交互。
- 非视觉模型试图新引入图片时返回 HTTP 422 和 `IMAGE_INPUT_NOT_SUPPORTED`。
- 当前分支已有 `ImageBlock` 却选择非视觉模型时返回 HTTP 409 和 `VISION_MODEL_REQUIRED`。
- 未从最早旧图片锚点升级却选择视觉模型时返回 HTTP 409 和 `LEGACY_IMAGE_CONTEXT`。
- 同一请求命中多项时，先判断既有分支约束：已有 ImageBlock 优先视觉必需错误；视觉模型遇到未升级旧图优先 legacy 错误；其余新图片冲突返回不支持错误。
- 会话详情以及发送、编辑、重新生成成功响应都返回 `image_context`，包含三态与可空的最早 legacy 消息 ID；只有 legacy 状态携带该 ID。
- 会话列表不返回图片上下文状态，避免列表扫描 transcript；前端不得自行解析附件或猜测状态。

### 前端交互

- 模型选择器根据 capabilities 与后端 `image_context` 呈现可用模型。视觉依赖时禁用非视觉模型；legacy 普通发送时禁用视觉模型；合法锚定编辑/重新生成时允许视觉模型。
- DeepSeek 图片拦截必须覆盖文件选择器、粘贴和拖放三条入口，并发生在任何上传 API 调用之前。
- 视觉模型下允许纯图片发送；发送按钮仍要求所有图片完成 ready 状态。
- 无视觉模型时只禁用消息变更操作，不妨碍历史阅读和会话管理。
- API machine code 映射到稳定恢复动作，不解析英文 detail。
- 产品不增加任何视觉隐私通知；兼容性说明只在操作无法完成时出现。

### 标题、分享与可观测性

- 自动标题继续只使用首条用户文字、安全附件元数据和首条助手回复，不再次读取图片 URL。纯图片首轮可使用文件名、格式、大小和助手回复；没有成功助手回复时不生成标题。
- 公开分享继续只保存附件占位，不包含原件、preview、派生物或读取许可。助手回复中的图片理解文本可随会话回复公开。
- 禁止记录预签名 URL、bucket、object key、文件名、图片哈希和完整 provider 请求体。
- 允许记录内部 Run ID、provider/model、图片数量、resolver 耗时、安全失败分类、provider request ID 和汇总 input usage。
- 监控至少覆盖 resolver 成功率、失败率、耗时、每次调用图片数、图片 input usage、preview backfill 剩余量和失败量。

### 存储隔离、backfill 与发布

- 新增独立私有 preview bucket。保留既有 upload、file-worker、canonical download 三个凭证角色；新增 preview API read 与 preview LLM read 两个角色；file-worker 角色增加 preview write/delete，共五组隔离凭证。
- 相关配置包括 preview bucket、API preview 读凭证和 LLM preview 读凭证。LLM Worker 显式清空 staging、canonical download 和 file-worker 写凭证。
- API 可签发 canonical 原件下载与 preview 浏览许可，但不能写 preview；file-worker 负责新 preview 写入、迁移和删除；provider 只获得单对象短期 GET URL。
- 新上传图片直接把 preview 写入新 bucket，原件继续写入 canonical bucket。
- 旧 preview 使用相同确定性 object key 复制到新 bucket；目标已存在时校验大小和 SHA-256。校验成功后，数据库事务切换存储位置并创建旧 canonical 对象删除补偿。
- 复制后、数据库切换前崩溃时，下次任务验证目标后继续。切换后、旧对象删除前崩溃时，既有删除补偿继续重试。
- 迁移期资产删除必须同时为旧位置和新 bucket 同 key 的潜在副本建立删除补偿；删除不存在对象视为成功。
- 迁移期间用户 preview 按行存储位置双读，模型 resolver 只接受新位置；排空后移除双读兼容。
- 发布顺序为：创建 bucket 和凭证；维护窗口执行 schema 切换并协调发布；视觉白名单保持为空；开始新写入并完成旧 preview backfill；确认剩余与失败为零；完成真实 R2 + `gpt-5-mini` 冒烟和全量检查；最后同时重启 API 与 LLM Worker 开启视觉能力。
- 回滚时清空视觉白名单并重启 API/LLM Worker；不改写 transcript、不回迁 preview、不删除新 bucket。文件生命周期、backfill 和删除补偿继续运行。

## Testing Decisions

- 好测试只断言外部可观察行为：HTTP 状态与 machine code、数据库中的当前消息/Run/transcript 事实、捕获到的 provider wire、对象存储可见副作用、用户界面可用动作和安全日志输出；不锁定内部私有函数调用顺序。
- **主测试缝：会话命令 HTTP 边界。** 复用现有 ASGI + 真实 PostgreSQL + fake provider/files adapter 的会话与 Run 集成测试。在这一最高层接缝覆盖四个 Run 创建入口、候选分支校验、三类图片上下文、事务失败零副作用、编辑解除约束、最早 legacy 锚点、重新生成更新当前 Run、失败/取消不回退和 mutation 响应状态。先例是现有会话 API、会话服务、重新生成、Run transcript 与 history 测试。
- **Provider 合同缝：中立内容块到 wire。** 复用现有 OpenAI/DeepSeek adapter 测试并注入 fake resolver，覆盖混合块顺序、不可信边界、文件名与首帧 warning、固定 high detail、同次去重、每次调用新 URL、任一图片失败时零 provider 请求，以及 DeepSeek fail-closed。该缝是 provider wire 无法从 HTTP 响应直接观察时保留的最小辅缝。
- **文件生命周期缝：files 服务 + fake R2。** 复用现有解析、对象存储、处理生命周期、维护与删除补偿测试，覆盖 `image-v1` 快照、独立存储位置、签名权限、copy/verify/switch、崩溃续跑、确定性双删和不存在对象幂等删除。
- **前端交互缝：用户可见组件与 hooks。** 复用现有 Composer、附件上传、模型偏好、消息编辑/重新生成和 API client 测试，覆盖选择/粘贴/拖放拦截、混合文件三动作、GPT 草稿切换 DeepSeek、纯图片发送、模型禁用、会话恢复优先级、只读模式和 machine code 恢复路径。
- 配置与 schema 合同测试覆盖视觉白名单合法/非法组合、capabilities 模型级字段、直接 schema 替换及 transcript 图像块严格往返。
- 预算测试只验证接纳行为：每图 8,192 预留、目标 turn 超限在 Run 前拒绝、历史按完整 turn 裁剪；不把 provider 当前计费公式复制为实现细节测试。
- 日志安全测试捕获失败路径输出，断言 URL、bucket/key、文件名、哈希和完整请求不存在，同时保留安全聚合字段。
- 真实冒烟使用一张带随机醒目标识的安全测试图：首轮纯图片要求读出标识；第二轮不重新附图要求引用细节；缩短测试 TTL 后等待过期并重新进入继续提问；核对 R2 access log 只读取 preview bucket；核对应用日志无敏感图片数据。
- 自动化验收包含后端测试、lint、类型检查，以及前端单元测试、lint、类型检查和生产构建。只有 backfill 剩余为零、失败为零、真实冒烟成功和全量检查通过后才能开启视觉白名单。

## Out of Scope

- DeepSeek 图片理解、OCR 后转文字给 DeepSeek，或任何自动 provider 切换。
- Provider Files API、长期 provider 文件、transcript 内 Base64 图片或长期图片 URL。
- 把附件原件发送给 LLM provider。
- 为视觉输入新增独立于现有 preview 的第二种派生物；只有未来输入与预览契约真实分化时再设计。
- 用户可配置图片 detail；首版固定 high。
- 图片 OCR、视频、GIF 新增支持或多帧动画理解；动画 WebP 仅使用现有首帧 preview。
- 文档页面视觉、扫描 PDF、图表或文档内嵌图片的视觉理解。
- 自动标题任务再次读取图片。
- 在公开分享中开放图片 preview、原件或下载能力。
- 图片发送通知、首次隐私提示或逐次确认。
- conversation-level 固定模型字段、持久化视觉状态位或会话列表 transcript 扫描。
- 长期 expand/contract 兼容、旧客户端兼容或不停机删除 `model_consumable`；本期采用已确认的维护窗口一步切换。
- 精确复制 OpenAI 图片计费公式；首版使用保守接纳预留并用真实 usage 后续校准。

## Further Notes

- 官方文档确认 `gpt-5-mini` 支持图片输入、WebP 和 Chat Completions；生产能力仍以显式白名单与真实连通性冒烟为准。GPT-5.6 可作为未来候选，但不能仅凭官方声明自动启用。
- `processor_version` 不是随意的数据库版本号。它标识“用哪套处理规则生成模型所见字节”；即使两个 preview 当前哈希相同，处理算法升级后仍可区分输入契约。
- 视觉依赖由当前有效消息分支决定，而不是“会话最初选择过哪个模型”。没有图片输入的 DeepSeek 会话可以切换 GPT；移除全部当前图片后也可回到 DeepSeek。
- 重新生成是合法的历史视觉升级入口，因为它会基于目标用户消息创建新的 Run transcript。关键要求是更新该消息的当前 Run 引用，而不是强迫用户先编辑。
- 本规格由已确认的完整设计讨论直接合成，状态为 `ready-for-agent`；如需拆分实施顺序和阻塞关系，应另行运行 ticket 拆分流程。
