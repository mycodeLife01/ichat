# 发送后消息置顶滚动（Send-anchored scrolling）

- 日期：2026-09-26
- 范围：live 对话页 `.thread-region` 的滚动行为（`frontend/src/messages/useStickToBottom.ts`、`frontend/src/app/AppShell.tsx`）
- 不涉及：分享页、独立 Design workbench、后端

## 1. 背景

旧行为：发送消息时 `useStickToBottom` 的 forceKey 变化，强制滚到底部并进入 pinned 跟随。消息占满
屏幕后，新发送的用户消息总是停在屏幕底部、紧贴 Composer，只有 AI 回复足够长才会把它顶上去；
用户视线被迫长期停留在屏幕下沿，大屏尤其疲劳。

## 2. 产品需求

| # | 场景 | 期望 |
|---|---|---|
| R1 | 内容已较多时发送新消息 | 新用户消息滚到可视区顶部（保留顶部间距），像本屏第一条消息，回复在其下方向下生长；桌面端上一条回复的操作栏不露出 |
| R2 | 对话很短，新消息自然位置已在屏幕上部 | 不做置顶，保持自然位置，不制造空白 |
| R3 | 回复生成中 | 视口不跟随流式文本；回复超出一屏后在屏幕外继续生成，出现“滚动到底部”按钮。用户主动滚回最底部时恢复原有跟随 |
| R4 | 生成结束后 | 预留空白不成为真实内容：结束瞬间画面不跳；用户滚动后空白只缩不涨，再滚回底部时只到真实内容末尾 |
| R5 | 进入 / 刷新 / 切换对话 | 保持旧行为：定位到底部，无预留空白 |
| R6 | 重新生成、编辑后重新生成 | 与发送一致：目标是线程中最后一条用户消息 |
| R7 | 用户在生成中主动滚动 | 尊重用户，不抢位置；“滚动到底部”指向真实内容末尾 |

边界：

- 用户消息过高（附件 + 回复引用 + 折叠后 320px 正文最坏约 850px）时，不强行对齐顶部，而是保证
  消息底部与回复开头至少 120px 可见。
- 移动端键盘、Composer 高度变化、窗口 resize、图片加载、长消息折叠测量（`Message` 在 effect
  中才应用 320px 折叠，首帧高度偏大）都必须在预留期内被重新计算，且画面不跳。
- 搜索定位与回复引用跳转（`pauseFollowing`）优先级保持不变。
- `prefers-reduced-motion` 下置顶为瞬时滚动；否则用 `requestAnimationFrame` 驱动 440ms
  ease-out（cubic）动画，起步快、收尾干脆、无回弹，不使用浏览器原生 smooth scroll（Chromium
  按距离缩放，约 800px 需 ~460ms，显得拖沓）。动画期间预留变化会让动画直接改向新目标；
  wheel / touchstart / pointerdown 立即中断动画并交还给用户。

## 3. 设计

### 3.1 三种滚动模式

`useStickToBottom` 由 `pinned` 布尔改为三态：

| 模式 | 进入 | 行为 |
|---|---|---|
| `bottom` | 进入对话、点击“滚动到底部”、用户向下滚到真实末尾附近 | 旧 pinned 行为：内容变化时贴真实末尾 |
| `anchored` | 发送 / 重新生成 / 编辑后重新生成后，新 Turn 出现时 | 视口停在锚点 T，不跟随流式文本；维持预留 |
| `free` | 用户主动滚动离开锚点或底部 | 只同步“滚动到底部”按钮，并收缩残余预留 |

### 3.2 触发

- AppShell 在真正提交前调用 `anchorNextTurn()` 进行“布防”，记录当时的 turnKey
  （`pendingSubmission.clientId ?? activeRun.runId`）。
- turnKey 变化（发送出现乐观消息 / 重新生成的新 Run 开始）时触发一次置顶并撤防。发送时乐观消息
  到服务端消息的切换沿用同一个 render key，不会再次触发。
- forceKey 只表示“进入对话”（会话 id）。草稿会话首条消息创建会话时（上一个 key 为空且处于
  anchored），不重置为 bottom。

### 3.3 锚点 T

以滚动容器内容坐标计算：

- `gap` 按断点取值，与消息的 `scroll-margin-top`（60px，搜索定位与回复引用跳转使用）独立：
  - 桌面 40px：上一条回复的操作栏（复制、重新生成）完整移出视口顶部，画面更干净；右上角
    “更多操作”与右对齐的用户气泡横向不重叠。与新会话首条消息的自然位置（`.thread-inner`
    `pt-10`）一致。
  - 移动端（`max-width: 760px`）60px：右上角浮动按钮下沿约 52px，且与右对齐的用户气泡横向
    重叠，40px 会产生遮挡。
- 自然末尾 `N = 有效 scrollHeight - clientHeight`；若新消息在 N 处的视口位置不超过
  `clientHeight / 3`，视为 R2，`T = N`（固定，不随回复增长而改变）。
- 否则 `T = max(消息顶部 - gap, 消息底部 - (clientHeight - Composer 区高度 - 120))`，
  第二项即超高消息保护。

### 3.4 可收缩底部预留

预留通过 `.thread-stage` 的 inline `min-height` 实现，只在内容下方增加空间，不改变任何已渲染
消息或流式锚点的几何（符合 AGENTS.md streaming surfaces 规则）。

- **预留（anchored）**：`min-height = T + clientHeight - Composer 区高度 - stageTop`，保证能滚到 T。
  回复变长时真实内容自然撑开，滚动高度在超出前保持恒定、视口不动。锚定期间对用户消息、滚动容器、
  Composer 区做 ResizeObserver，重新计算 T 与预留（覆盖折叠测量、键盘、resize、图片加载）。
- **收缩（离开 anchored 后）**：每次滚动把 `min-height` 缩到“刚好保持当前 scrollTop 合法”的
  值，只缩不涨；不再需要时移除。生成结束本身不删除预留，因此结束瞬间不跳；用户上翻后，空白消失。
- 下一次发送重新计算新的预留，但**不先清除旧预留**：否则滚动高度瞬间变小，浏览器把 scrollTop
  夹回真实内容末尾，动画会从更早的内容重新滚过来。置顶动画期间预留同时覆盖当前位置与目标位置，
  落定后再收紧到目标所需值。效果是用户不滚动直接连续发送时，只有当前这一轮向上推进。
- 进入其他对话时直接清除。

### 3.5 有效底部

“滚动到底部”按钮的显示阈值（136px）、`isNearBottom` 判断与一键到底的目标都基于**真实内容末尾**
（`.thread-inner` 最后一个子元素底部 + 其 padding-bottom + Composer 区高度），而不是含预留的
`scrollHeight`。

## 4. 验收

jsdom 只覆盖状态机；几何必须在真实 Chromium 中测（桌面 1440×900 与移动 390×844）：

1. 内容已满时发送：用户消息 `top - 滚动容器 top` ≈ gap（桌面 40px、移动 60px，±2px）；桌面端
   上一条回复的操作图标完全位于视口之外。
2. 回复未超出预留时，流式过程中 `scrollTop` 与 `scrollHeight` 恒定。
3. 生成结束那一帧 `scrollTop` 不变，用户消息 top 不变。
4. 结束后滚到顶部再滚到底部：最大 `scrollTop` 等于真实内容对应的最大值（无残余空白）。
5. 短对话发送：不置顶、无预留。
6. 进入历史对话仍定位到底部。
7. 超高用户消息：消息底部与回复开头可见。
8. 允许动效时，置顶动画从开始移动到落定在 350–470ms 之间，位移单调、无越界回弹。
9. 置顶后不滚动直接再次发送：整个过程 scrollTop 只增不减（不回滚到更早内容），新消息落在 gap 处。
