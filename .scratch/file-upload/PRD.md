# 统一文件上传与消息附件

Type: feature
Status: ready-for-human
Blocked by: None

日期：2026-08-01
需求来源：本分支 `grill-with-docs` 设计确认会话
术语依据：根目录 `CONTEXT.md`（文件上传 / 文件资产 / 文件对象 / 文件用途 / 消息附件 / 文档块 / 附件提示块 / 附件输入预算 / 删除会话）
相关决策：ADR 0001–0005，以及既有“账户注销 = 软停用 + 延后物理清除”决策

## Problem Statement

iChat 当前只有头像这一种文件上传能力。头像链路已经具备浏览器直传 Cloudflare R2、PostgreSQL 状态行、Celery 唤醒、worker 验证与转码、公开对象替换、删除补偿和 CDN purge，但这些能力全部封装在头像专用模型与模块中。用户无法在聊天中上传图片、文档、数据文件或源代码，也无法让模型读取文档内容。

产品现在需要把上传能力扩展为统一文件领域：头像与消息附件共享上传、存储、任务、配额和删除生命周期，同时继续保持用途隔离。消息附件必须支持常见图片、PDF、Office、文本、数据和代码格式；文档内容必须经过服务端安全验证和提取后才能进入模型上下文，图片本期只上传、预览和下载，不提供视觉理解。

该需求不能通过简单扩大头像 MIME allowlist 完成。头像具有“每用户一个当前值、公开 CDN、替换原子切换、不保留原件”的语义，而消息附件具有“多个私有文件、保留原件、生成文档派生文本、绑定消息、受上下文预算约束”的语义。如果继续维护两套上传状态机，会复制 claim、lease、重试、临时对象清理、外部写入补偿和删除逻辑；如果把两种用途粗暴压进一张万能表或散落的 purpose 分支，又会让公开头像权限污染私有附件。

系统还必须解决不可信文档解析、恶意软件、ZIP bomb、格式伪装、上传后对象覆盖、并发配额、孤儿 R2 对象、页面关闭与显式取消竞态、模型上下文溢出、公开会话分享泄漏、软删除后配额无法释放、现有头像数据迁移和生产回滚等问题。

## Solution

建立一个统一且足够深的 `files` 领域模块，向调用者暴露创建上传、确认上传、查询/取消、绑定附件、签发读取许可和回收文件等少量 interface。上传状态机、文件资产、物理对象、配额、输出 manifest、维护扫描和删除补偿全部由该模块拥有；头像和消息附件是模块内部两个固定且不可互换的文件用途。

领域模型分为三层：`FileUpload` 表达一次有期限、可失败和可重试的上传流程；`FileAsset` 表达处理成功后可被业务使用的不可变逻辑文件；`FileObject` 表达 R2 中的原件、缩略图、文档派生文本或头像成品。用户头像通过显式外键引用文件资产，消息通过显式附件关联引用文件资产，不使用无法建立真实外键的多态用途表。

浏览器仍然把字节直接 PUT 到私有 staging bucket。API 在创建上传会话前执行 active、邮箱验证、allowlist、限流、并发与配额预留；confirm 通过 HEAD 验证大小、元数据和 ETag 后把 PostgreSQL 状态提交为 queued，再尽力发送 Celery 唤醒。worker 使用 confirm ETag 做条件下载，计算 SHA-256，执行恶意软件扫描和真实格式验证，并在受资源限制的子进程中解析文件。worker 在向正式 bucket 写对象前先持久化输出 manifest，确保崩溃或数据库故障后能够回收外部副作用。

头像继续由 media-worker 处理并写公开头像 bucket；消息附件由独立 file-worker 处理并写私有正式 bucket。两个 worker 共享 files 模块的状态机实现，但使用不同 queue、进程、凭证和 claim 过滤条件。不可信 PDF/Office 解析器不能获得头像公开 bucket、Cloudflare purge、邮件或 LLM Secret。

消息附件保留用户原件并生成用途所需的文件派生物。文本、代码、数据、PDF 和 Office 文档由 iChat 提取为完整 `DocumentBlock`，不调用 provider Files API；图片本期只生成安全预览和 `AttachmentNoticeBlock`。消息和附件采用全有或全无事务绑定。模型实际读取的完整文档派生文本进入 Run transcript，使旧 Run 的事实不依赖 R2 或未来解析器版本。

文件生命周期有明确期限：pending 上传 30 分钟，ready 但待绑定文件 24 小时，脱离当前消息修订的附件 30 天，软删除会话 30 天后物理清除。所有 R2 删除使用持久化对象删除补偿；公开头像额外要求 CDN purge。每用户消息附件配额为 1 GiB，按原件大小计量，并通过 PostgreSQL 配额状态行事务性维护 used 与 reserved 字节。

## User Stories

1. 作为已验证邮箱的 active 用户，我想在聊天输入区选择文件，以便把本地资料带入对话。
2. 作为用户，我想一次选择多个附件，以便同时让模型比较多份资料。
3. 作为用户，我希望一条消息最多支持五个附件，以便功能可用且界面不会失控。
4. 作为用户，我希望一条消息的附件原件总大小最多为 50 MiB，以便在上传前获得明确限制。
5. 作为用户，我想上传 JPG 或 JPEG 图片，以便在消息中展示常见照片。
6. 作为用户，我想上传 PNG 图片，以便保留透明背景或无损图像。
7. 作为用户，我想上传静态 WebP，以便使用体积较小的现代图片格式。
8. 作为选择动画 WebP 的用户，我想得到明确拒绝提示，以便知道本期只支持静态图片。
9. 作为选择超大尺寸图片的用户，我想在上传前或处理阶段得到明确错误，以便避免无休止等待。
10. 作为用户，我想看到去元数据后的安全图片预览，以便确认将要发送的附件。
11. 作为用户，我想下载自己上传的图片原件，以便附件仍代表我实际提交的文件。
12. 作为用户，我理解本期模型不能读取图片内容，以便不会误以为模型看过图片。
13. 作为随文字附带图片的用户，我希望模型知道存在一张当前不可读取的图片，以便模型能够诚实说明限制。
14. 作为只选择图片且未输入文字的用户，我希望发送按钮说明为什么不能发送，以便避免创建没有模型可见输入的 Run。
15. 作为用户，我想上传 PDF，以便让模型读取可选择的文本内容。
16. 作为上传扫描 PDF 的用户，我想知道本期不提供 OCR，以便理解为什么完全无文本的文件被拒绝。
17. 作为上传混合 PDF 的用户，我想让可提取页面正常进入模型，同时看到扫描页未被读取的警告。
18. 作为用户，我想上传 DOCX，以便让模型读取可见正文和表格。
19. 作为用户，我想上传 PPTX，以便让模型读取可见幻灯片文字。
20. 作为用户，我想上传 XLSX，以便让模型读取工作表、单元格、公式和缓存结果。
21. 作为上传 XLSX 的用户，我希望系统绝不执行公式或访问外部数据连接，以便文件处理保持安全。
22. 作为上传含隐藏工作表的用户，我希望隐藏内容默认不发送给模型，以便避免无意泄露。
23. 作为上传含演讲者备注的用户，我希望备注默认不发送给模型，以便私有备注不会意外出境。
24. 作为上传含批注或已删除修订的用户，我希望模型只读取最终可见主体内容，以便结果符合正常阅读视图。
25. 作为上传受密码保护文档的用户，我想收到要求本地解除保护的提示，以便理解系统不会索取或保存密码。
26. 作为上传损坏 Office/PDF 的用户，我想收到稳定错误提示，以便重新导出文件。
27. 作为用户，我想上传 TXT 和 Markdown，以便直接让模型阅读普通文本。
28. 作为用户，我想上传 CSV，以便让模型分析有限规模的表格数据。
29. 作为用户，我想上传 JSON，以便让模型阅读或修复结构化数据。
30. 作为用户，我想上传 YAML 或 YML，以便让模型阅读常见配置文件。
31. 作为开发者用户，我想上传 Python、JavaScript、TypeScript、Go、Java 和 SQL 文件，以便讨论代码。
32. 作为上传无效 JSON、YAML 或代码的用户，我希望文件仍能进入模型，以便请求模型帮助修复语法。
33. 作为上传旧编码文本的用户，我想得到“请转为 UTF-8”的明确提示，以便避免模型读取乱码。
34. 作为用户，我希望文件原件保持不变，以便下载时得到与上传一致的字节。
35. 作为用户，我希望系统为模型生成独立的安全派生文本，以便内部规范化不会覆盖原件。
36. 作为用户，我希望扩展名与真实格式不一致时文件被拒绝，以便下载和模型解析语义不会错乱。
37. 作为上传 OOXML 的用户，我希望系统验证容器内部真实类型，以便改名 ZIP 不能伪装成 Office 文件。
38. 作为用户，我希望上传流量直接进入 R2，以便 FastAPI 不成为大文件带宽瓶颈。
39. 作为用户，我希望短期上传 URL 只允许写入服务端指定的随机对象 key，以便我的身份和文件名不出现在对象路径中。
40. 作为网络不稳定的用户，我希望同一个有效单次 PUT 可以有限重试，以便偶发网络错误不要求立即重建会话。
41. 作为用户，我接受本期不提供分片和断点续传，以便第一版保持简单可靠。
42. 作为用户，我希望上传完成后看到扫描和处理中的离散状态，以便知道文件尚未丢失。
43. 作为用户，我希望多个附件通过一个合并轮询流程更新，以便前端不会发起过多高频请求。
44. 作为用户，我希望附件全部 ready 后才能发送消息，以便 Run 不需要等待另一个任务状态机。
45. 作为用户，我希望任一附件失败时整条消息不被静默发送，以便模型不会漏读我以为已经附带的文件。
46. 作为用户，我希望上传处理暂时失败时自动重试，以便短暂 R2、扫描器或基础设施故障不会要求重传。
47. 作为处理最终失败的用户，我想看到可理解且不泄露内部堆栈的错误，以便决定是否重新上传。
48. 作为明确点击取消的用户，我希望后端阻止 queued 文件继续产生业务文件，以便取消具有真实语义。
49. 作为直接关闭页面的用户，我理解关闭页面不是可靠取消，以便系统可以通过上传期限和待绑定期限兜底回收。
50. 作为刷新页面的用户，我希望 queued、processing 和 ready 附件卡片能够恢复，以便不必重新等待已经完成的后端工作。
51. 作为在 PUT 中途刷新页面的用户，我接受重新选择本地文件，以便系统不必实现断点续传。
52. 作为用户，我希望刷新和查看附件不会延长待绑定文件期限，以便上传功能不会变成隐形文件库。
53. 作为用户，我想在发送前预览图片或下载待绑定原件，以便确认所选文件正确。
54. 作为用户，我希望待绑定文件超过 24 小时自动回收，以便未发送草稿不永久占用配额。
55. 作为用户，我希望消息可以只有一个模型可消费文档附件而没有文字，以便直接上传文档发起对话。
56. 作为纯附件消息用户，我希望系统不伪造“请分析此文件”等用户文字，以便聊天历史忠实记录我的输入。
57. 作为用户，我希望消息文字和附件保持独立，以便编辑、展示、分享和 token 计算不会被内部派生文本污染。
58. 作为用户，我希望附件按选择顺序进入消息和模型，以便多文件引用顺序稳定。
59. 作为用户，我希望编辑消息时默认继承原附件，以便只修改文字不要求重新上传。
60. 作为用户，我希望编辑请求可以显式增加、删除或重排附件，以便控制新消息修订的完整输入。
61. 作为用户，我希望直接重新生成时复用原消息附件，以便重新生成不会改变输入事实。
62. 作为用户，我希望从当前消息修订移除的附件不会永久占用配额，以便编辑后可以释放存储。
63. 作为用户，我希望脱离所有当前消息引用的附件保留 30 天，以便误编辑不会立即造成不可逆字节删除。
64. 作为系统维护者，我希望删除会话后后端保留 30 天恢复事实，以便必要时可通过 API 处理；前端不展示已删除会话或恢复入口。
65. 作为用户，我希望删除会话 30 天后自动物理清除附件并释放配额，以便删除最终有实际效果。
66. 作为系统维护者，我希望通过后端恢复会话时附件仍然可预览和下载，以便恢复后的会话保持完整。
67. 作为用户，我希望下载附件时获得原始文件名和原始字节，以便文件可以正常保存到本地。
68. 作为用户，我希望附件下载 URL 只短期有效，以便复制或泄露的 URL 不能长期访问私有内容。
69. 作为用户，我希望软删除会话或停用账户后无法再签发附件 URL，以便私有数据立即失去新访问入口。
70. 作为用户，我希望消息图片通过安全派生物预览，以便浏览器不直接渲染未经处理的原件。
71. 作为用户，我接受本期 PDF、Office、代码和文本只显示文件卡片与下载按钮，以便不引入复杂文档阅读器。
72. 作为用户，我希望部分可读文档在文件卡片中显示警告，以便知道模型没有看完整个视觉文档。
73. 作为用户，我希望同一警告也进入模型输入，以便模型能够在回答中说明限制。
74. 作为用户，我希望附件完整进入模型而不是静默截断，以便关键结尾不会无提示丢失。
75. 作为附件过大的用户，我希望发送前得到上下文预算错误，以便拆分文件或减少附件。
76. 作为用户，我接受本期不提供 RAG 或附件摘要模式，以便模型输入语义保持明确。
77. 作为用户，我希望当前目标 turn 在 256k 总预算下最多使用 128k estimated tokens，以便仍有空间保留系统提示和历史。
78. 作为用户，我希望旧历史按完整 turn 裁剪，以便“分析这份报告”不会与报告附件分离。
79. 作为用户，我希望旧 Run 精确保留当时模型读取的附件文本，以便未来解析器升级不会改写历史事实。
80. 作为用户，我希望模型不会执行附件中的“忽略系统提示”等指令，以便文件正文始终被视为低信任数据。
81. 作为用户，我希望 iChat 只把派生文本而不是附件原件发送给 provider，以便减少不必要的数据出境。
82. 作为切换模型的用户，我希望文档解析结果保持一致，以便 provider 变化不会悄悄改变文件内容。
83. 作为选择不支持某类输入模型的用户，我希望发送前得到明确 capability 错误，以便系统不会自动切换模型。
84. 作为用户，我希望自动标题根据用户文字、附件元数据和首条助手回复生成，以便纯文档会话也有合理标题。
85. 作为用户，我希望标题任务不再次发送完整文档，以便避免重复 token 消耗和数据出境。
86. 作为创建公开会话分享的用户，我希望附件原件、预览和派生文本默认不公开，以便分享对话不会自动变成文件分享。
87. 作为访问公开分享的人，我希望看到附件文件名、格式和大小占位，以便理解对话上下文中曾有附件。
88. 作为分享含附件会话的用户，我希望在创建链接前看到额外隐私警告，以便理解助手回复可能已包含文件信息。
89. 作为用户，我希望一个文件资产只有一个固定用途，以便私有附件不会因“设为头像”意外公开。
90. 作为用户，我希望同一字节内容跨用途时产生不同逻辑资产，以便删除和保留规则互不污染。
91. 作为用户，我希望头像继续采用现有裁剪和原子替换体验，以便文件领域统一不会造成头像退化。
92. 作为用户，我希望头像只保留公开成品而不保留上传中间图，以便头像用途继续满足现有隐私语义。
93. 作为用户，我希望新头像成功前旧头像保持可见，以便替换失败不会出现空头像。
94. 作为完成账户注销的用户，我希望公开头像立即删除并 purge CDN，以便旧公开 URL 不再可用。
95. 作为完成账户注销的用户，我理解私有消息附件随可恢复业务数据暂时保留，以便注销语义与现有 ADR 一致。
96. 作为用户，我希望每人拥有明确的 1 GiB 消息附件配额，以便知道可以保留多少文件。
97. 作为并发上传多个文件的用户，我希望配额在创建上传时预留，以便多个请求不能共同突破上限。
98. 作为用户，我希望失败、取消和过期上传释放预留配额，以便无效流程不会永久占用空间。

103. 作为平台运营者，我希望每 IP 每小时最多创建 500 个会话，以便共享网络可用但仍有限制。

108. 作为平台运营者，我希望 processing lease 过期后任务可恢复，以便 worker 崩溃不会永久卡住文件。
109. 作为平台运营者，我希望重复 Celery 消息无法让终态任务再次执行，以便任务满足幂等要求。
110. 作为平台运营者，我希望暂时故障最多处理三次，并按 30 秒和 5 分钟退避，以便避免任务风暴。
111. 作为平台运营者，我希望解析子进程最多运行 120 秒，以便病态文件不能无限占用 CPU。
112. 作为平台运营者，我希望整次处理尝试最多 180 秒且 lease 为五分钟，以便有限任务不需要持续 heartbeat。
113. 作为平台运营者，我希望内容超限与基础设施故障使用不同终态，以便不会对恶意文件反复重试。
114. 作为平台运营者，我希望所有原件先经过恶意软件扫描，以便降低已知恶意样本风险。
115. 作为平台运营者，我希望扫描器不可用或签名过期时失败关闭，以便未扫描文件不能成为可用文件。
116. 作为平台运营者，我希望扫描通过后仍在受限子进程解析，以便病毒扫描不是唯一安全边界。
117. 作为平台运营者，我希望不可信文档使用独立 file-worker，以便解析漏洞不泄露头像和无关 Secret。
118. 作为平台运营者，我希望 file-worker 只持有私有文件 bucket 最小权限，以便凭证泄露影响可控。
119. 作为平台运营者，我希望头像任务和附件任务使用不同 queue，以便 Office 处理不会阻塞头像。
120. 作为平台运营者，我希望 staging 与 canonical 文件使用不同私有 bucket，以便 CORS、权限和生命周期可独立配置。
121. 作为平台运营者，我希望上传签名、worker 和下载签名使用不同最小权限凭证，以便单一入口泄露不扩大权限。
122. 作为平台运营者，我希望 worker 按 confirm ETag 条件读取，以便 confirm 后覆盖对象不能绕过确认。
123. 作为平台运营者，我希望所有正式输出 key 在写 R2 前先进入数据库 manifest，以便外部副作用可回收。
124. 作为平台运营者，我希望每个文件对象删除都有持久化补偿，以便 R2 故障不会造成永久泄漏。
125. 作为平台运营者，我希望公开头像删除同时完成 R2 删除和 CDN purge，以便统一模型不削弱隐私删除。
126. 作为平台运营者，我希望对象不存在被视为删除成功，以便重试保持幂等。
127. 作为平台运营者，我希望配额状态有周期 reconciliation，以便计数漂移能够发现和修复。
128. 作为平台运营者，我希望文件名、内容和签名 URL 不进入日志，以便敏感资料不会复制到长期观测系统。
129. 作为平台运营者，我希望日志只记录 ID、状态、大小、耗时和稳定错误码，以便可排障且不泄密。
130. 作为平台运营者，我希望看到 queue wait、扫描、解析和 R2 写入分段耗时，以便定位处理延迟。
131. 作为平台运营者，我希望图片和文本 P95 在 10 秒内 ready，以便常见附件体验流畅。
132. 作为平台运营者，我希望 PDF/Office P95 在 30 秒内 ready，以便容量规划有明确目标。
133. 作为平台运营者，我希望正常文件 P99 在 120 秒内 ready，以便异常任务可以被识别。
134. 作为运维人员，我希望能查询 queued、processing、failed、删除补偿和配额状态，以便处理积压与用户支持。
135. 作为运维人员，我希望能在依赖恢复后重新触发 due 任务，以便不需要直接修改 R2 对象。
136. 作为运维人员，我希望看到 ClamAV 签名更新时间和扫描失败率，以便扫描链路失效能被发现。
137. 作为运维人员，我希望开发与生产使用独立 bucket 和凭证，以便 smoke 测试不会污染生产。
138. 作为开发者，我希望 files 模块拥有一个高层 interface，以便调用者不需要理解 R2、lease、扫描器和删除补偿。
139. 作为开发者，我希望 R2、ClamAV、解析器和 provider 都通过 adapter 替换，以便普通测试不依赖外部网络。
140. 作为开发者，我希望头像与消息附件共享上传骨架但保留内部用途策略，以便复用不会变成散落条件分支。
141. 作为开发者，我希望上传流程、逻辑资产和物理对象分别建模，以便失败上传不会伪装成业务文件。
142. 作为开发者，我希望头像和消息附件使用显式外键关系，以便 PostgreSQL 可以保证引用完整性。
143. 作为开发者，我希望本期记录 SHA-256 但不物理去重，以便删除、权限与账户清除保持简单可靠。
144. 作为开发者，我希望现有头像 HTTP 契约保持兼容，以便前端迁移可以分阶段完成。
145. 作为开发者，我希望只迁移现有当前头像而不转换所有历史上传，以便数据库迁移不依赖 R2。
146. 作为开发者，我希望旧头像状态与补偿自然排空后再删除旧表，以便新旧生命周期不会留下未完成外部副作用。

148. 作为前端开发者，我希望 capabilities 返回格式、大小、数量和图片模型能力，以便限制变更不要求重新发布前端。
149. 作为前端开发者，我希望 capabilities 关闭时仍能展示已有附件，以便回滚不破坏历史消息。
150. 作为测试人员，我希望所有竞态通过可复现外部行为验证，以便实现重构不会改变正确性。

## Implementation Decisions

### 模块与 interface

- 终态建立一个统一的 `files` 领域模块，拥有文件上传、文件资产、文件对象、配额、回收、删除补偿和用途策略。
- 头像与消息附件是 files 模块内部两个固定用途。用途在创建上传时确定且不可变，跨用途操作创建新的逻辑文件资产。
- 调用者通过高层 interface 创建/确认/查询/取消上传、绑定消息附件、获取读取许可及触发回收；调用者不接触 bucket、对象 key、lease、扫描器或补偿实现。
- R2、恶意软件扫描器、文件解析器、任务 publisher、下载 signer 和 provider 是内部 adapter seam。生产 adapter 与 fake adapter 通过同一 interface 测试。
- 现有头像 HTTP 路径保持兼容，但迁移完成后删除独立头像领域模块。Cloudflare purge 保持头像用途内部行为。
- 客户端不能自由传 purpose。头像入口由服务端固定为 avatar，普通文件入口固定为 message_attachment。
- 文件附件使用独立功能开关。关闭只停止新增上传，不停止已有文件读取、queued/processing 排空、删除补偿或回收。

### 持久化模型

- 使用 `file_uploads` 表表达上传流程，至少记录随机 public ID、用户、用途、声明文件名/类型/大小、临时对象 key、确认 ETag、状态、尝试次数、available_at、lease、错误码、有效期、输出 manifest、成功 file ID 和清理时间。
- 使用 `files` 表表达成功后的不可变文件资产，至少记录随机 public ID、用户、用途、原始文件名、真实媒体类型、原件大小、SHA-256、处理警告、提取器版本和生命周期时间。
- 使用 `file_objects` 表表达物理对象，至少记录所属文件、role、storage location、object key、媒体类型、大小、SHA-256 和创建时间。
- 使用 `message_attachments` 显式关联 Message 与 FileAsset，并保存顺序和分享所需的稳定元数据。禁止多态 entity_type/entity_id 关联。
- 用户当前头像改为显式 avatar file ID 外键，不再以 object key 作为最终领域引用。
- 使用每用户一条事务性配额状态行维护 `used_bytes` 与 `reserved_bytes`。所有增减与上传/文件状态在同一事务提交，并提供周期 reconciliation。
- 使用持久化 `file_object_deletions` 表记录待删除 object key、storage location、可空 purge URL、分步完成时间、尝试次数、available_at、错误摘要和完成时间。
- 不建立物理去重或 blob 引用计数。本期每个文件资产拥有独立对象；SHA-256 仅用于完整性、重复识别、排障和未来优化。

### 上传 interface 与状态机

- 消息附件提供创建上传、confirm、查询状态、显式取消、预览许可和下载许可 interface；头像路由内部复用同一上传骨架。
- 创建上传前验证 active、邮箱已验证、格式 allowlist、单文件大小、每用户配额、用户/IP 限流和每用户在途数量。
- 消息附件限流为每用户每小时 100 次、每 IP 每小时 500 次，每用户最多五个 pending/queued/processing 上传。Redis 故障时 fail-closed。
- 创建上传时锁定配额行并按 declared size 增加 reserved。失败、取消、过期释放 reserved；成功按实际原件大小转入 used。
- 使用单次预签名 PUT，不提供 multipart 或断点续传。签名固定随机 key、内容类型和声明大小元数据。
- confirm HEAD 临时对象并核对大小、声明大小、ETag 和元数据；confirm 幂等，首次确认后的 ETag 不可更换。
- worker 必须使用 If-Match 条件读取确认 ETag 对应的对象，再计算 SHA-256 和验证长度。ETag 不作为长期内容哈希。
- 状态机为 pending → queued → processing → succeeded/rejected/failed，并允许暂时故障回 queued；pending 可 expired；pending/queued/processing 可 cancelled。
- succeeded 表示已经创建 FileAsset；rejected 表示同一内容的永久策略/安全失败；failed 表示暂时故障三次耗尽；expired 表示会话超时；cancelled 表示显式取消、账户停用或头像被更新意图取代。
- 最大处理尝试三次；第一次暂时失败 30 秒后重试，第二次暂时失败 5 分钟后重试，第三次进入 failed。available_at 是 PG 事实，Celery countdown 只是加速。
- 解析子进程 wall-clock 上限 120 秒，整次尝试上限 180 秒，processing lease 五分钟，不做持续 heartbeat。解析资源超限直接 rejected，外部暂时故障才重试。
- 显式取消与成功最终提交锁定同一上传行。取消先提交则不得产生业务文件；成功先提交则取消操作回收尚未绑定的资产。关闭页面不等于可靠取消。

### R2 与执行拓扑

- 每个环境使用独立私有 staging bucket 与私有 canonical files bucket；头像继续使用公开成品 bucket。开发和生产完全隔离。
- 上传签名凭证仅允许 staging PUT/HEAD；file-worker 可条件读取/删除 staging 并读写删 canonical；下载 signer 仅允许 canonical GET；media-worker 持有头像公开 bucket 权限；Cloudflare purge 使用独立 Token。
- object key 使用随机 UUID 且不包含用户 ID、用户名、邮箱、文件名或时间序列。
- files 模块共享状态机，但 avatar 上传路由 media queue/media-worker，message_attachment 路由 files queue/file-worker。worker claim 按用途和 storage location 过滤。
- file-worker 不持有头像公开 bucket、Cloudflare purge、邮件或 LLM 凭证。不可信解析在资源受限子进程内执行。
- Celery beat 保持单实例并周期投递 sweep。PostgreSQL 状态行是任务事实，Celery/Redis 只作可丢失唤醒。
- worker 在写 canonical 对象前持久化 output manifest。崩溃、取消或最终数据库提交失败时，维护任务根据 manifest 对所有可能输出执行幂等删除。
- 所有正式对象删除进入 `file_object_deletions`。私有对象以 R2 删除完成为终态；公开头像要求 R2 删除与 CDN purge 都完成。

### 格式、安全与处理策略

- 精确扩展名 allowlist：jpg、jpeg、png、webp、pdf、docx、pptx、xlsx、txt、md、csv、json、yaml、yml、py、js、ts、go、java、sql。
- 扩展名必须与真实内容匹配；浏览器 MIME 只作初筛。JPG/JPEG 为同一格式；OOXML 必须验证容器内部类型。
- 图片单文件最大 10 MiB，仅静态单帧，最长边 8192、总像素 2000 万。完整解码验证，原件私有保存，预览使用去元数据安全派生物。
- PDF 单文件最大 25 MiB、最多 200 页，只提取可选择文本，不做 OCR、页面渲染、批注、附件、脚本或视觉理解。
- DOCX/PPTX/XLSX 单文件最大 20 MiB；OOXML 解压后总大小最大 100 MiB、entry 数最大 10,000，拒绝路径穿越、嵌套压缩和异常压缩比。
- PPTX 最多 200 张可见幻灯片；XLSX 最多 50 个可见工作表和总计 100,000 个实际非空单元格；DOCX 最多 100,000 个可提取节点。
- CSV 最多 100,000 行且每行最多 256 列。文本、数据和代码单文件最大 2 MiB。
- 文本、数据和代码只接受 UTF-8/UTF-8 BOM，拒绝 NUL 和严格解码失败。派生文本移除 BOM 并规范化换行为 LF，原件不改变。
- JSON、YAML、CSV 和源代码不要求语法有效，不执行、不反序列化为业务对象；文件内容始终是低信任用户数据。
- XLSX 提取工作表、单元格地址、公式文本和文件内缓存值，不执行公式、不重新计算、不访问外部连接。
- Office/PDF 只提取正常可见主体内容；排除隐藏工作表/行列、隐藏幻灯片、演讲者备注、批注、已删除修订、交互动作和文档属性。
- 所有加密或密码保护的 PDF/Office 文件拒绝，不接受密码或异步等待解密。
- 所有原件在解析前通过 ClamAV/clamd。命中恶意签名永久 rejected；扫描器不可用或签名过期时 fail-closed 并按暂时故障重试。
- 部分存在可提取语义内容的文档可以 ready，但持久化稳定 warning 并同时展示给用户和写入 DocumentBlock；完全没有可提取内容的文档 rejected。
- 原始文件名只存业务元数据；进行 Unicode 规范化、路径剥离、长度限制和响应头安全转义。日志、指标和异常摘要不得包含文件名或文件内容。

### 消息、编辑与 Run

- 每条用户消息最多五个附件，原件总大小最多 50 MiB。后端按已验证文件大小计算。
- 发送请求携带有序 attachment IDs。后端验证所有权、purpose、ready 状态、待绑定期限、数量、总大小、provider capability 与附件输入预算。
- Message、全部 message attachments、待绑定保护和 Run 在同一事务创建；任一附件失败则不创建消息或 Run。
- `messages.content` 只保存用户实际文字，可以为空。附件关系、文件元数据及派生文本不拼接进该字段。
- 用户消息必须有非空文字或至少一个模型可消费附件。仅展示图片不能单独满足发送条件。
- 图片本期不进入模型视觉上下文，但生成 AttachmentNoticeBlock，包含安全文件名、类型和当前不可读取事实；不包含字节、URL、OCR 或视觉描述。
- 文本、代码、数据和文档生成完整 DocumentBlock。DocumentBlock 包含文件身份、完整派生文本、摘要、提取器版本和 warning。
- iChat 自行提取文档，不使用 provider Files API，不向 provider 上传原件。provider adapter 只投影中立内容块。
- 当前实际 context budget 为 256,000 tokens；目标用户 turn 最多 128,000 estimated tokens 且不超过总预算 50%。超限拒绝发送，不截断、不摘要、不做 RAG。
- 上下文历史按完整 turn 裁剪，用户文字和附件不可分离；目标用户 turn 永不裁剪。
- 模型实际读取的完整 DocumentBlock 快照进 Run transcript，并记录 file identity、hash 与 extractor version；旧历史回放不依赖 R2。
- 编辑消息时 attachment IDs 省略表示继承，显式列表表示完整替换，空列表表示全部移除。直接重新生成固定复用原附件。
- 自动标题使用用户文字、附件安全元数据和首条助手回复，不再次注入完整附件正文。

### 读取、前端与分享

- API 不代理文件字节；鉴权后签发五分钟 R2 GET URL。preview 指向安全图片派生物并 inline，download 指向原件并 attachment。
- 待绑定文件在有效期内按所有者授权读取；绑定后按当前可见 MessageAttachment 关系授权。终态无效文件、软删除会话和停用账户不签发新 URL。
- 本期只有图片提供内容预览。PDF、Office、文本、数据和代码显示文件名、格式、大小、状态、warning 与下载按钮。
- 前端必须等待全部附件 ready 后才能发送。使用合并状态轮询，建议从一秒退避至五秒；页面不可见时暂停，不新增文件 SSE。
- 前端按用户和会话草稿保存 upload/file IDs、顺序和文字；刷新恢复后端已有状态，但不中断续传 PUT。登出或切换账号清理本地草稿。
- capabilities 动态返回开关、allowlist、分类大小、最多附件数、每消息总大小、目标 turn token 上限和图片模型能力。前端预校验不能替代后端执行。
- 公开会话分享只保存附件占位元数据，不包含原件、派生物、预览或下载 URL。含附件会话创建分享时增加隐私确认，说明助手回复可能包含附件信息。

### 生命周期、配额与账户

- pending 上传会话 30 分钟过期；ready 未绑定文件 24 小时后回收；读取、刷新或打开编辑器不续期。
- 脱离所有当前消息修订引用的附件进入 30 天回收期；归档消息保留元数据，旧 transcript 保留当时文档块。
- 删除会话进入 30 天可恢复期，期间附件继续保留并占用配额；到期后物理清除会话、消息、Run 和附件，并在同一事务创建对象删除补偿。
- 每用户消息附件配额为 1 GiB，按原件字节计量。bound、unbound 和删除恢复期内文件都计入；头像不占消息附件配额。
- 文件资产进入删除流程时释放 used 配额，即使外部 R2 删除仍由补偿重试；补偿积压必须单独监控实际存储。
- 账户注销继续采用软停用：禁止新上传和新下载 URL，失效在途上传；私有已绑定附件随业务数据保留。公开头像仍立即解除引用、删除 R2 并 purge CDN。
- 头像替换仍原子切换：新头像成品和数据库提交成功前旧头像保持可见；头像 FileAsset 只保留公开 512×512 WebP 成品，不保留上传中间图。

### 迁移、部署与回滚

- 采用 additive migration：先增加统一文件表、配额表、删除补偿和可空 avatar file ID，保留旧 avatar object key。
- 只迁移每个用户当前有效头像：为现有公开对象创建 avatar FileAsset 与 avatar_512 FileObject。迁移不访问 R2，历史大小/hash 可以标记 legacy import。
- 应用短期优先读取 avatar file ID 并回退旧 key；新上传只写新模型。完成映射验证后移除回退和旧字段。
- 旧头像上传与删除表继续完成现有 queued/processing/补偿；积压清零且历史保留期结束后再删除，禁止直接截断。
- 新文件上传使用独立功能开关。上线顺序为数据库与读取兼容、worker、API 创建入口、前端入口；回滚先停止新增，再排空状态与补偿。
- 新增私有 staging/canonical bucket、CORS、最小权限凭证、file-worker、ClamAV 和单实例 beat 调度配置。普通 CI 使用 fake，不持有生产 Secret。

### 可观测性与体验目标

- 日志只记录 upload/file/user IDs、purpose、状态、格式类别、大小、页数/节点/单元格数、token 估算、耗时和稳定错误码。
- 禁止记录原始文件名、原件/派生文本、完整签名 URL、文档属性、未经清洗的 parser 异常或临时本地路径。
- 分别监控 queue wait、条件下载、ClamAV、解析、R2 写入、最终提交、清理和删除补偿耗时与失败率。
- 监控 queued/processing/failed/rejected 数量、processing lease 过期数、最老补偿、配额 reconciliation 漂移、ClamAV 签名年龄和 file-worker 资源终止次数。
- confirm 到 ready 的目标：图片/文本/代码/小数据 P95 ≤ 10 秒；PDF/Office P95 ≤ 30 秒；正常文件 P99 ≤ 120 秒。浏览器 PUT 时间不计入。

## Testing Decisions

### 测试 seam

- 最高且主要的测试 seam 是统一 files 模块的外部 interface。大多数测试通过创建上传、确认、处理、绑定、读取许可、取消和回收等可观察结果验证整个模块，而不是分别锁定内部 helper 或表字段赋值顺序。
- API 测试穿过 FastAPI 路由、认证依赖、files interface 与数据库事务，使用 fake storage/publisher/scanner/parser，验证 HTTP contract 和所有权。
- worker 测试穿过单次“按 upload ID 处理”interface，使用真实数据库状态行与 fake adapters，验证 claim、lease、重试、manifest、终态和外部对象结果。
- Agent 测试穿过 Message/ContentBlock 与 provider adapter interface，验证 DocumentBlock、AttachmentNoticeBlock、token 预算和 transcript round-trip，不测试私有序列化 helper。
- 前端测试穿过上传编排函数、composer 用户交互和消息提交 interface，mock HTTP/R2 fetch，不测试实现内部 state hook。

### 先例

- 上传创建、confirm、状态轮询、R2 fake、worker 处理、lease、维护和删除补偿沿用现有头像 API、storage、processing 与 maintenance 测试形状。
- 消息与 Run 原子创建、编辑/重新生成、归档和活动 Run 保护沿用会话模块集成测试。
- ContentBlock 持久化、provider 投影和 transcript round-trip 沿用现有 agent message、provider adapter 和 transcript 测试。
- 整 turn 裁剪与 token 预算沿用 agent context 测试，并新增目标 turn 过大必须拒绝的上层用例。
- 账户停用、注销、公开头像例外沿用账户生命周期测试；公开分享附件占位沿用分享快照测试。
- 前端上传恢复、消息附件卡片、分享警告和 capabilities 沿用现有 avatar 上传、composer、store 与分享组件测试。

### 必测行为

- 创建上传：active/邮箱验证、allowlist、单文件限制、100/500 限流、五个在途上限、1 GiB 并发配额预留和 Redis fail-closed。
- confirm：所有权、过期、对象缺失、大小/元数据/ETag 不匹配、幂等重复和 publish 失败后 PG 状态保留。
- 条件读取：confirm 后对象覆盖导致 If-Match 失败，原内容不会被替换为业务文件。
- 状态机：所有允许转移、终态不可重入、三次重试与 30 秒/5 分钟 available_at、lease owner 不匹配不能提交。
- 取消竞态：pending/queued、processing、R2 已写未提交、success 先提交、cancel 先提交、关闭页面不产生虚假取消。
- output manifest：每个故障注入点都可由维护任务删除可能存在的 canonical 对象，不需要 bucket 全量扫描。
- 恶意软件：命中 rejected；扫描器暂时不可用重试；签名过期 fail-closed；日志无内容泄漏。
- 格式检测：所有 allowlist happy path；扩展名伪装；OOXML 内部类型错误；动画/像素炸弹；加密、损坏、ZIP bomb、XXE/路径穿越与复杂度上限。
- 提取语义：PDF 页标记、DOCX 可见正文表格、PPTX 可见 slide、XLSX 公式+缓存值、隐藏内容排除、无文本 rejected、部分文本 warning。
- 文本：UTF-8/BOM、非法编码、NUL、换行规范化、无效 JSON/YAML/代码仍可 ready、CSV 行列上限。
- FileAsset/FileObject：仅 succeeded 创建；消息附件保留 original 与派生物；头像只保留 avatar_512；purpose 不可改变。
- 消息绑定：最多五个、总计 50 MiB、全有或全无、所有权、ready、purpose、待绑定期限、provider capability、128k target turn budget。
- 纯附件消息：文档可发送；纯图片拒绝；文字+图片生成 notice；`messages.content` 不含派生文本。
- 编辑/重新生成：省略继承、显式替换、空列表移除、顺序稳定、直接 regenerate 固定复用、脱离附件进入 30 天。
- transcript：DocumentBlock 完整快照与 round-trip、hash/version/warning、历史回放不访问 R2、附件内容仍是低信任数据。
- context：目标 turn 永不裁剪且超限拒绝；旧 turn 整体裁剪；文字、文档和工具序列不被拆开。
- 下载：待绑定所有权、绑定后消息可见性、五分钟 URL、preview/download role、停用/软删除/删除中拒绝、header 转义、日志无 URL。
- 分享：附件只产生占位；匿名接口无法下载；含附件创建额外确认；assistant 既有内容保持快照。
- 配额：reserved/used 全部事务路径、失败释放、删除释放、软删除 30 天仍占用、reconciliation 检测并修复漂移。
- 回收：pending 30 分钟、unbound 24 小时、detached 30 天、conversation deletion 30 天，读取不续期，恢复会话取消到期清除。
- 删除补偿：私有单步、头像双步、404 幂等、部分成功续跑、DB 关系清除后仍能完成、worker 权限隔离。
- 账户注销：在途取消、无新下载、私有附件保留、公开头像删除/purge，运维恢复不恢复旧头像。
- 迁移：现有 current avatar 映射、legacy metadata、双读回退、新写新模型、旧任务排空、upgrade/downgrade 或明确不可逆保护。
- capabilities：动态限制与开关；前端隐藏新入口但仍展示已有附件；后端始终重复执行限制。
- 前端：五文件卡片、上传/处理/失败状态、合并轮询、页面可见性、刷新恢复、取消、ready 前禁发、附件 warning、图片预览、下载和分享警告。

### 外部集成与验收

- 普通 CI 全部使用 fake adapters，不依赖 R2、ClamAV 网络或 provider Files API。
- 增加独立 ClamAV 集成测试，使用官方无害测试签名验证命中路径，不保存真实恶意样本。
- 在开发 R2 做真实 smoke：预签名 CORS、ETag 暴露、If-Match、staging/canonical 权限、短期 GET、Content-Disposition、对象清理和跨 Origin 拒绝。
- 在受控开发环境对 PDF/OOXML corpus 做资源限制与提取 golden tests，覆盖正常、部分可读、加密、损坏和恶意容器。
- 验证 compose 开发/生产配置、file-worker queue 隔离、凭证最小权限、beat 单实例和功能开关回滚。
- 容量验收采集确认到 ready 的分段指标，并验证目标 P95/P99；性能测试不得使用生产用户文件。
- 后端完成 pytest、ruff、mypy；前端完成 vitest、lint、typecheck、build；compose 配置完成开发与生产校验。

## Out of Scope

- 图片视觉理解、ImageBlock、OCR、图片文字提取和自动图像描述。
- 扫描 PDF OCR、PDF 页面渲染、PPTX slide 渲染、图表理解和嵌入图片理解。
- RAG、向量索引、分块检索、附件摘要、静默截断或抽样输入。
- provider 原生 Files API、provider 文件托管或向第三方上传原件。
- 独立用户文件库、跨无关消息复用、跨用途复用和文件夹管理。
- 同用户或跨用户物理去重、共享 blob、引用计数和基于 hash 的存在性响应。
- multipart upload、分片合并、断点续传和中断 PUT 恢复。
- 加密/密码保护文档解密、密码保存或交互式后台等待。
- GIF、动画 WebP、SVG、HTML、XML、TOML、RTF、DOC、PPT、XLS、ZIP 及 allowlist 外源码格式。
- PDF/Office/代码的浏览器内阅读器；本期非图片附件只提供卡片与原件下载。
- 公开附件下载、公开预览、匿名签名 URL 或附件 CDN；公开会话只含占位元数据。
- 用户从归档历史任意挑选并复用附件。
- 独立删除已绑定文件而保留当前消息内容；附件通过消息修订和生命周期回收。
- 将账户注销改为 30 天后自动物理清除整个账户；既有软停用 ADR继续有效。
- 自动模型切换或因附件类型改变 provider/model。
- 细粒度文件处理 SSE、页面级进度和虚构百分比。
- 对历史已存文件进行周期性全量恶意软件重扫；本期只在进入 ready 前扫描。
- 实施 ticket 拆分；本 PRD 只定义完整产品和技术规格。

## Further Notes

- 最高测试 seam 已由前序设计会话确认：统一 files 模块 interface。R2、ClamAV、parser、publisher、download signer 和 provider 是内部 adapter seam；不要为 avatar/attachment 再暴露平行的外部生命周期 interface。
- 统一领域不代表统一权限。media-worker 与 file-worker 的隔离是安全部署决策，不应被后续“减少容器数量”重构静默撤销。
- `context_budget_tokens` 实际生产值为 256,000；仓库默认值目前可能不同。实施时必须校准默认、环境模板、测试和 capabilities，避免不同环境的附件接纳行为漂移。
- 现有头像 PRD 明确写过“不建设通用文件资产领域”。该约束已被新的真实附件需求和 ADR 0002 取代；实施完成时必须更新模块架构文档，但历史 PRD 保持原样作为当时决策记录。
- 删除会话 30 天后物理清除与脱离附件 30 天后回收是新增不可逆生命周期，必须提供恢复期 UI、到期时间、运维查询、批处理上限和删除补偿监控。
- 公开分享虽然不包含文件字节，但助手回复可能包含文件信息。额外确认是必要提示，不是后端附件过滤的替代品。
- 文件内容、文件名和 parser 异常都可能包含敏感信息。测试 fixture 使用合成数据，日志断言应验证敏感字段从未出现。
- 任务表必须持续满足项目后台任务三问：最大尝试三次；30 秒/5 分钟退避；永久策略错误进入 rejected，暂时故障耗尽进入 failed，删除补偿保留到完成。
- 实施结束后需要新增中文 handover、部署与 R2/ClamAV smoke 文档，并更新文档索引、架构总览和模块职责。
